# 프로토타입 — 코어 루프 (M1)

씬: `Assets/_Game/Scenes/Proto_Chapter01.unity` → **Play 누르면 바로 플레이 가능**
재생성: Unity 메뉴 **Tools ▸ 좀비 오버런 ▸ 프로토타입 씬 생성**

필드 씬(`Field_Chapter01`)을 읽어 그 위에 플레이어와 시스템을 얹어 별도 씬으로 저장한다.
따라서 `필드 생성`을 다시 돌려도 프로토 씬은 살아남는다. 순서는 **필드 생성 → 좀비 애니메이션 셋업 → 프로토타입 씬 생성**.

**수치는 코드가 아니라 에셋에 있다** (2026-11-05): 적 7종·보스/습격/엘리트 일정은 `Data/Enemies` + `Resources/Data/EnemyTable`,
캐릭터 ↔ 무기 ↔ 필사기 연결은 `Data/Characters` + `Resources/Data/CharacterTable`, 필사기 수치는 `Data/Ultimates`, 무기는 `Data/Weapons`.
구조와 "새로 붙이는 순서"는 [`Scripts/Data/README.md`](../Data/README.md). `ProtoConfig` 에는 게임 전체의 성질(플레이어 공통·피격 느낌·스폰 예산·수식)만 남았다.

## HUD (`ProtoHUD`) — uGUI (2026-10-06, IMGUI 에서 옮김)

캔버스를 **코드로** 짓는다(Awake). 씬 배선은 예전 그대로(`run`·`player`·`director` 3개)라 모든 프로토 씬에서 바로 뜬다.
- `CanvasScaler` 1080×1920 기준, match 0.5. HUD(바·타이머·버튼)는 `Screen.safeArea` 안, 전면 화면(레벨업·결과·옵션)은 화면 끝까지.
  레벨업 상자(1040×1200)·옵션 판(900×1380)은 고정 크기라 가로 에디터 화면(높이 ~1080 단위)에서는 `FitBox` 로 줄인다.
- 형제 순서 = 그리는 순서: HUD < 레벨업 < 결과 < TAP TO SKIP < 옵션.
- **레벨업 화면 = 원작 팝업(2026-11-13)**: `Resources/Data/SkillSelectSkin.asset` 이 있고 `useThisPopup` 이 켜져 있으면 위의 코드 카드 대신
  Survivor Ace 사본 `UI_DankeSkillSelect_Sample`(`_Reference/SurvivorAce/UI/SkillSelect`)을 `ProtoSkillSelectPopup` 이 띄운다(별도 캔버스, 정렬 20, Expand).
  카드 · 아이콘 · 노랑(무기)/파랑(능력치) · 별 · 보유 줄 · 새로고침/건너뛰기 → `run.PickCard/Reroll/SkipCards`. 프리팹에서 끈 부분(지금 보유 줄 · 새로고침)은 꺼진 채.
  원작 그림 임시 사용 — 출시 전 교체. 자세한 것은 그 폴더 README '게임 연결'.
- 필사기 버튼 = 원 + **게이지 링**(Image Filled Radial360, 스프라이트는 코드로 생성 — §14 'H · 액티브 버튼').
- **UI 위 터치는 이동이 아니다** — `ProtoPlayer.PointerOverUI()` 가 EventSystem 으로 거른다(IMGUI 시절엔 버튼을 누르면 캐릭터가 걸어갔다). EventSystem 이 씬에 없으면 HUD 가 만든다(StandaloneInputModule — 옛 입력).
- 글자는 `UnityEngine.UI.Text` + 내장 `LegacyRuntime.ttf`(OS 한글 대체). **한글 TMP 폰트 에셋이 없어서** TMP 를 안 썼다. 정식 폰트가 정해지면 TMP 로.
- 클리어 애니는 `ProtoSpritePopup` 이 시계·소리·시트만 쥐고(`TryGetClear`/`Sheet.UV`) HUD 가 RawImage 로 그린다. 필사기 컷인은 2026-10-29 사용자 요청으로 삭제(시트·소리 파일 포함).
- IMGUI 로 남은 것: 캐릭터 교체 패널(ProtoCharacterSwitcher), 카메라 각도 표시(ProtoCameraFollow) — 디버그 도구라서.
- **검증 팁**: 오버레이 캔버스는 `Camera.Render` 에 안 찍힌다. 캡처할 때만 `ScreenSpaceCamera` 로 바꾸고, RT 크기로 `CanvasScaler.Handle`(리플렉션) → `ProtoHUD.LateUpdate`(리플렉션)를 한 번 돌린 뒤 렌더하면 세로 1080×1920 화면이 그대로 찍힌다.

## 데미지 숫자 (`ProtoDamageText`) — 밀도에 맞춰 자동

사용자 결정(2026-10-06): 처음 A안(중요한 것만)으로 넣었다가, 사용자가 실제 밀도(화면에 좀비 20~30)로는 부담이 없다고 봐서 **자동 방식**으로 바꿨다.
- **중요한 피해**(치명타 = 노랑·큰 글자, 보스, 큰 한 방 = 로켓 폭발·융단 폭격·교체 피해·필사기)는 항상.
- **평범한 피해**(잡좀비가 맞는 탄·화염·블레이드)는 떠 있는 숫자가 `CrowdLimit`(12) 개 미만일 때만, 작게(0.34m)·짧게(0.5초). 밀도가 기획서 목표(300)로 오르면 저절로 A안이 된다.
- **같은 대상의 0.5초 안 피해는 하나로 합친다**(모든 좀비). 캐논 0.08초 연사·화염 틱이 줄줄이 쌓이지 않게. 치명타가 섞이면 노랑, 중요한 피해가 섞이면 제 크기. 0.3초였을 땐 소총(0.35초)이 매 발 따로 떴다.
- 판정 지점은 `ProtoZombie.DealDamage` 한 곳(flash 경로만 — 화상 틱은 숫자 없음). 큰 한 방은 `TakeDamage(amount, dir, crit, bigHit:true)`.
- **숫자 전부 메시 하나·드로우콜 하나**. 동시 24개, 넘치면 오래된 것부터. 막 뜬 숫자 옆이면 위로 비켜 쌓는다.
- 아틀라스 `Resources/VFX/T_DamageDigits.png`(+ .json 글자 폭) = `ArtSource/VFX/make_damage_digits.py`(Impact, 흰 글자+검은 외곽선 → 정점 색).
  셰이더 `Proto/DamageText`(ZTest Always, 큐 Overlay+100), 빌드 포함은 `Resources/ShaderRefs/Ref_Proto_DamageText.mat`.

위 내용은 **기존 식**(`Style.Classic`)이다. 2026-11-10 부터 기본은 아래 YAZS 식이고, 옵션 "데미지 숫자"가 **YAZS 식 → 기존 → 꺼짐**으로 돈다(`ProtoSettings.DamageStyle` 0/1 · `CycleDamageNumbers()`).

### YAZS 식 (`Style.Yazs`, 2026-11-10 — 사용자 요청 "피해 숫자도 YAZS 처럼 DamageNumbersPro")

Yet Another Zombie Survivors 는 **Damage Numbers Pro**(에셋 스토어 유료 에셋)를 쓴다. **그 플러그인은 넣지 않았다** — 프로젝트에도 이 PC 의 에셋 스토어 보관함에도 없고,
추출본(`D:\YetAnotherZombieSurvivors_1.0.1a`)의 `DamageNumbersPro.dll` 은 함수 본문이 없는 껍데기(34KB)인 데다 남의 라이선스라 제품에 넣을 수 없다.
대신 YAZS 가 그 플러그인에 넣어 둔 **설정값**(프리팹 `Damage Number (Mesh)` · `_Crit`)을 읽어 `ProtoDamageText` 에 같은 연출을 넣었다. 숫자마다 TextMeshPro 오브젝트를 만드는 플러그인과 달리 여전히 메시 하나·드로우콜 하나다.

| | YAZS 프리팹 값 (DNP 항목) | 우리 (`ProtoDamageText` 상수) |
|---|---|---|
| 일반 글자 | PT Sans Narrow Regular, 외곽선 0, 흰색, 글자 em 0.2m | 얇고 좁은 흰 글자(옅은 그늘 한 겹), 칸 높이 `YHeight` = 0.2 × `YSizeScale`(2.38) = **0.48m**(숫자 자체 약 0.33m) |
| 치명타 글자 | PT Sans Narrow Bold, 검은 외곽선 0.1, em 0.4m(= 2배) | 굵은 글자 + 얇은 검은 외곽선, `YHeightCrit` = 0.4 × `YSizeScale` = **0.95m**(2배), 노랑 |
| 떠 있는 시간 | lifetime 1 / 치명타 2, 나타남 0.2 + 사라짐 0.2 | `YLife` 1 · `YLifeCrit` 2 · `YFadeIn` 0.2 · `YFadeOut` 0.2 → 1.2초 / 2.2초 |
| 움직임 | Lerp: speed 5, X −0.4~0.4, Y 0.5~1 (무작위 자리로 미끄러져 가서 멈춤) | `YDriftSpeed` 5 · `YDriftX` 0.4 · `YDriftYMin/Max` 0.5/1 — 값 그대로 |
| 치명타가 나타날 때 | Scale 2 + Cross Scale 4 + Shake (0, 1.5) 주파수 4 | 같은 방식, 단 Cross Scale 은 **1.6**(`YCritCross`), 잔상 불투명도 0.35 |
| 치명타가 사라질 때 | Scale 0.4 | `YCritScaleOut` 0.4 |
| 합치기 | Combination 꺼짐 — 맞을 때마다 한 개 | 합치지 않는다(기존 식의 0.5초 합치기·위로 비켜 쌓기 없음) |
| 붐빌 때 | "많으면 80 이상만"(`DamageDisplayThresholdWhenMany`), 풀 64 + 32 | 동시 `MaxPopups` 64, 평범한 피해는 떠 있는 숫자가 `YazsCrowdLimit`(32) 미만일 때만 |

- **크기 실측(2026-11-10, 사용자 질문 "원래 이렇게 작은가? YAZS 화면에서 어느 정도로 나오는지 분석해서 비슷하게").** 스팀 상점의 홍보 스크린샷에는 피해 숫자가 꺼져 있어,
  스팀 커뮤니티에 올라온 실제 플레이 스크린샷(1920×1080)을 브라우저 캔버스로 픽셀 단위로 읽었다.

  | 1080p 화면에서 | YAZS 실측 | YAZS 프리팹 값으로 계산 | 우리(`YSizeScale` 1.7) |
  |---|---|---|---|
  | 일반 숫자 높이 | 11px (화면 높이의 1.0%) | 11.9px | 20px (1.8%) |
  | 치명타 숫자 높이 | 24px (2.2%) | 23.8px | 40px (3.7%) |
  | 캐릭터 키 | 91px (약 1.8m) | 92px | 148px (2.7m — Visual 1.598배) |
  | 일반 숫자 ÷ 캐릭터 키 | 12% | — | 13% |
  | 치명타 숫자 ÷ 캐릭터 키 | 27% | — | 27% |

  결론: **YAZS 의 숫자는 원래 작다**(우리보다 더 작다). 배율 1.7 일 때 우리는 픽셀로 YAZS 의 1.7배, **캐릭터 대비로는 YAZS 와 같았다.**
  이 결과를 보고 사용자가 **"1.4배 키우기"를 골랐다** → `YSizeScale` **2.38**(= 1.7 × 1.4): 1080p 에서 일반 28px(2.6%) · 치명타 56px(5.2%),
  캐릭터 키 대비 19% · 38%. 가로로 쥔 6.5인치 폰에서 일반 숫자 약 1.8mm(1.7 일 땐 1.2mm). 같이 치명타 잔상 배율 `YCritCross` 를 2 → 1.6 으로 줄였다(잔상은 글자 크기에 비례해 커진다).
  크기는 `ProtoDamageText.YSizeScale` 하나로 고친다(1 = YAZS 와 똑같은 픽셀 크기). 카메라가 YAZS 와 같은 값(52° · 65° · 12m)이라 배율 1 이면 화면 픽셀도 같다.
  YAZS 숫자 색: 일반은 흰색보다 살짝 어두운 밝은 회색, 굵은 숫자는 흰색(다른 스크린샷에선 검붉은색 — 피해 종류별 색으로 보인다).
- **YAZS 와 다르게 둔 것과 이유.** ① 글자 크기 1.7배 — YAZS 는 PC 화면 기준(숫자 높이가 화면의 1%)이라 그대로면 폰(가로로 쥔 6.5인치, 화면 높이 약 68mm)에서 0.7mm 다. 일반 : 치명타 = 1 : 2 는 지켰다.
  ② Cross Scale 4 → 1.6 — 잔상은 글자 크기에 비례해 커진다. 글자 1.7배일 때 4 는 화면을 너무 크게 덮어 2 로 줄였고(프레임별 미리보기 그림으로 확인, 잔상 높이 약 1.7m), 글자를 2.38배로 키우면서 1.6 으로 더 줄였다(약 2.0m).
  ③ 일반 글자에 옅은 그늘 — YAZS 는 외곽선이 아예 없는데 우리는 불·총구 화염이 밝아 흰 글자가 묻힌다.
  ④ 가려지지 않게 그린다(ZTest Always) — YAZS 는 벽에 가려진다(renderThroughWalls 0).
- **못 읽은 것.** 치명타 색 — 프리팹엔 흰색이고 코드가 피해 종류별 색(`damageNumberColor`)을 넣는데 코드는 추출되지 않았다. 우리 노랑(`ColCrit`)을 유지했다.
- **폰트.** YAZS 의 PT Sans Narrow 파일은 넣지 않았다. 이 PC 에 깔린 **Noto Sans KR**(SIL OFL — 제품에 써도 된다)의 숫자를 가로로 0.80~0.84 눌러 좁은 글자를 만들었다.
  PT Sans Narrow(역시 OFL, Google Fonts)로 바꾸려면 `ArtSource/VFX/make_damage_digits_yazs.py` 의 `FONT` 와 `ROWS` 의 가로 누름(1.0)만 고쳐 다시 굽는다.
  참고로 기존 식 아틀라스는 Windows 의 Impact 로 구웠다 — 출시 때 기존 식을 남긴다면 그쪽 폰트 라이선스를 확인해야 한다.
- 아틀라스 `Resources/VFX/T_DamageDigitsYazs.png`(640×192 — 윗줄 일반, 아랫줄 치명타) + `.json`(`widths` · `widthsBold`). 없으면 기존 식으로 떨어진다.
- 치명타가 나타나는 0.2초 동안은 한 숫자를 두 벌(큰 잔상 + 본체) 그린다. 쿼드는 64×6 + 여유 96. 떠 있는 숫자가 없으면 메시를 다시 올리지 않는다.
- **화면 미확인.** 컴파일과 프레임별 미리보기 그림(같은 계산을 파이썬으로 옮겨 그린 것)까지만 봤다. 크기·시간은 `ProtoDamageText` 의 `Y…` 상수에서 고친다.

## 시작 연출 (`ProtoIntro`) — 비행기 → 낙하산 → 착지

런 시작·재시작마다 재생(약 4.5초). 아무 키 / 클릭 / 탭 = 건너뛰기. 그 동안 `RunState.Intro` 라 스폰·사격·타이머·이동이 멈춘다.
- Player 루트는 처음부터 바닥(시작 지점)에 있고 **공중에 있는 건 Visual 뿐**이다. 착지에서 Visual 로컬을 0 으로 되돌리고 Running.
- 카메라는 `ProtoCameraFollow.introZoom`(거리 배율 1.55→1)·`introLift`(초점 높이)만 만진다.
- 모델 `Resources/Intro/IntroPlane·IntroParachute.prefab`(= Field/Props airplane·parachute.fbx, 머티리얼 `M_Airplane`·`M_Parachute` BCM 툰 + 노멀맵).
  **두 FBX 의 텍스처 파일명이 같아(texture_pbr_20250901.png) 자동 임포트가 엉뚱한 쪽을 물었다** → 머티리얼을 직접 만들고 FBX 에 리맵.
- **낙하산 프리팹 루트에 스케일 100 이 걸려 있다**(FBX 단위 변환). localScale 을 덮어쓰면 0.03 배로 사라진다 — `_chuteBase` 에 곱한다.

### 자식을 갈아끼운 뒤 반드시 다시 잡아야 하는 것 3개

2. `ProtoShooter.RebindVisual()` — `Fire` 트리거가 아무 데도 안 간다(사격 애니가 죽는다).
3. `ProtoGroundRing.RaisePlayerQueue()` — 새 렌더러는 큐가 안 올라가 있어서 **링이 캐릭터를 덮는다**
   (아래 "렌더 큐" 절 참조). 여러 번 불려도 결과는 같다.

## 캐릭터 교체 연출과 교체 피해 (`ProtoCharacterSwitcher` + `ProtoLightningStrike`)

`Select()` 는 **즉시 바뀌지 않는다.** 번개가 지면에 닿는 순간에 맞춰 세 단계로 진행한다.

| 시각 | 일어나는 일 |
|---|---|
| 0.00s | 번개 재생 시작. 옛 몸이 줄어들기 시작 (`vanishTime` 0.09s) |
| 0.09s | 옛 몸 스케일 0 — 완전히 사라진 상태 |
| **0.10s** | **번개 착탄. 여기서 Visual 교체 + 주변 피해** (`ProtoLightningStrike.ImpactDelay`) |
| 0.10 → 0.21s | 새 몸이 1.15m 위에서 **가속하며 떨어진다**(t²). 떨어지는 동안 세로로 늘어남 |
| **0.21s** | **착지** — 세로 72%로 눌리고(스쿼시) 가로로 퍼짐 + 발밑 먼지 폭발 |
| 0.21 → 0.38s | 눌린 데서 1 로 돌아온다. 살짝 넘겼다 제자리(`BackOut`) |

이 사이에도 **이동·사격은 멈추지 않는다.** 게임플레이는 `Player` 루트에 있고 Visual 은 자식일 뿐이다.
패널 표시용 `Current` 만은 누른 즉시 갱신한다 — 반응이 없으면 입력이 씹힌 것처럼 느껴진다.

### 왜 그냥 커지게 두지 않았나

처음에는 새 몸이 0 → 1 로 커지기만 했다. **"뚝 나타났다"로 보였다.** 위에서 떨어뜨렸다가
바닥에서 한 번 눌러주면 같은 0.3초인데도 '도착했다'로 읽힌다 — 스쿼시&스트레치의 기본이다.

- **낙하는 등속이 아니라 t² 다.** 등속으로 떨어뜨리면 '내려놓는' 느낌이 된다.
- 떨어지는 동안 세로로 **늘어나고**(스트레치 1.18 → 1.0), 착지에서 **눌린다**(0.72).
  눌린 만큼 가로로 퍼지게 해야(`2 - landSquash`) 부피가 보존되는 것처럼 보인다.
- 착지 먼지는 번개 착탄(0.10s)이 아니라 **캐릭터가 바닥에 닿는 순간(0.21s)** 에 터진다.
  둘이 겹치면 번개 섬광에 묻혀서 아무도 못 본다.

튜닝 손잡이: `dropHeight`(1.15m) · `fallTime`(0.11s) · `landRecover`(0.17s) · `landSquash`(0.72).

**함정 1 — 불투명 머티리얼이 네모 판으로 나온다.**
`TinyStonesParticle` 은 `URP/Lit` 에 `_Surface=0`(Opaque) 이다. 파티클 빌보드에 물리면
알파가 없는 **흰 사각형**이 그대로 날아다닌다. `SandParticle`(`Particles/Lit`, `_Surface=1`)로 교체했다.

**함정 2 — `Particles/Lit` + 소프트파티클.**
`Dust.mat` 은 Lit 라서 직사광 아래에서 하얗게 뜨고, `_SOFTPARTICLES_ON` 이 켜져 있는데
**이 프로젝트의 URP 애셋은 Depth Texture 가 꺼져 있다**(깊이를 못 읽는다). 둘이 겹쳐
딱딱한 흰 다각형으로 나왔다. 사본 `M_SwapDust.mat` 을 만들어 **Unlit + 알파블렌드 +
소프트파티클 OFF** 로 바꿨다. 팩 원본은 안 건드렸다.

> **팩에서 부품을 뗄 때는 머티리얼의 `_Surface` 와 셰이더 이름을 먼저 확인할 것.**
> 이 팩에는 URP 로 변환 안 된 머티리얼이 **12개** 남아 있다
> (`Flame02`, `Embers`(Magic Effects 쪽), `PlasmaFire` 등 — `Legacy Shaders/*`, `Particles/Standard Unlit`).
> 우리가 쓰는 프리팹 3개는 전수 확인했고 지금은 전부 깨끗하다.

### 시간축은 unscaled 다

레벨업 카드가 떠 있는 동안 교체가 일어나면 `timeScale` 이 0 이다. `WaitForSeconds` 나
`Time.deltaTime` 으로 재면 연출이 통째로 얼어붙는다. `ProtoConfig.UnscaledDelta` 로 직접 누적한다
(번개도, 지면 파티클도 같은 이유로 unscaled).

### 스케일을 옛 Visual 에서 물려받으면 안 된다

예전 `Select()` 는 새 캐릭터의 크기를 **옛 Visual 의 `localScale` 에서 읽어** 물려받았다.
사라지는 연출이 붙은 지금 그 값은 0 에 가깝다 — 그대로 두면 교체할 때마다 캐릭터가 사라진다.
그래서 `_baseScale` 을 따로 캐시한다(`CacheBaseScale`, `Awake` 에서 한 번).

### 교체 피해 (`SwapBlast`)

```csharp
public static int SwapBlast(Vector3 center, float radius, float damage)   // 맞은 수를 돌려준다
```

- **거리 감쇠 없음.** 반경 안이면 전부 같은 값이다. 데미지 숫자를 안 쓰는 게임(§15)이라
  감쇠를 넣으면 "왜 얘만 안 죽었지"가 화면에서 읽히지 않는다.
- **판정 반경 = 지면 링 테두리.** `swapRadius` 기본 1.86m 은 `ProtoLightningStrike.GroundRingRadius`
  (프리팹 실측값)와 같다. 반경을 바꾸면 `Play()` 에 넘기는 `scaleMul` 이 연출을 같이 키운다 —
  **테두리가 곧 판정선**이어야 무엇이 맞았는지 읽힌다(착탄 폭발과 같은 원칙).
- **덩치 보정 있음.** 몸 반경이 기본(0.28)보다 큰 적은 그 초과분만큼 판정을 넓힌다.
  보스(0.55)는 중심만 재면 어깨가 링 안에 들어와 있는데도 안 맞는다.
  (`ProtoProjectile.Explode` 는 이 보정이 없다 — 거기도 넣을지는 미정.)

실측(에디터에서 좀비 인스턴스를 만들어 `SwapBlast` 를 그대로 호출):

| 거리 | 결과 |
|---|---|
| 0.00 / 1.00 / 1.80m | 각각 정확히 40 피해 |
| 1.90 / 2.50 / 4.00m | 무피해 |
| 2.00m, 몸반경 0.28 | 무피해 |
| 2.00m, 몸반경 0.55(보스) | 피해 — 덩치 보정이 먹었다 |

## 무기별 전투 수치 (`WeaponStats`)

`ProtoShooter` 는 더 이상 `ProtoConfig` 전역값으로 쏘지 않는다. 장착 무기의
`WeaponModelDef.stats` → `WeaponStats` 에셋(`Assets/_Game/Data/Weapons/Stats/`)에서 읽는다.
**`ProtoConfig.WeaponDamage/Interval/Range` 를 고쳐도 인게임은 안 바뀐다** — 그 셋은 수치 에셋이
안 물려 있을 때의 폴백일 뿐이다.

모델과 수치를 **다른 에셋**으로 나눈 이유: 아트가 FBX 를 다시 뽑는 일과 밸런스가 피해량을 만지는
일은 주기가 달라서, 한 파일에 있으면 서로의 변경을 덮어쓴다. 참조로만 묶는다.

| 무기 | 모드 | 피해 | 간격 | 사거리 | DPS | §05 DPS |
|---|---|---|---|---|---|---|
| 탕탕 소총 | Single | 12 | 0.35 | 9.0m | 34.3 | 34 |
| 산탄총 | Shotgun | 7×5 | 0.90 | 5.0m | 38.9 | 39 |
| 화염방사기 | Cone | 9/틱 | 0.20 | 4.5m (부채 50°) | 45.0 | 45 |
| 로켓 발사기 | Rocket | 50 | 1.70 | 11.0m (폭발 2.4m) | 29.4 | 29 |
| 탕탕 캐논 (진화) | Single | 45 | 0.08 | 9.0m (스프레드 8°) | 562 | — |

**회전 블레이드·지원 드론은 이 표에 없다** — 주무기가 아니라 카드로 얻는 보조 장비다(아래).
그래서 v1.0 주무기는 4종이고, 캐릭터 6종이 그 4종을 나눠 쓴다:
루키·리퍼 = 소총 / 브레이커 = 산탄총 / 파이로 = 화염방사기 / 데몰리셔·테크니션 = 로켓.
같은 무기를 쓰는 캐릭터는 §06 고유 패시브로 갈린다 — 캐릭터 확장 방어선 3번이 정확히 이 규칙이다.

`WeaponStats.Dps` 는 **필드가 아니라 계산**이다. 표에 적어두면 피해량을 고칠 때 한쪽만 고쳐져서
기획서와 대조할 때 어느 쪽이 진짜인지 알 수 없게 된다.

### 6가지 발사 모드

- `Single` — 투사체 1발. `spreadDegrees` 가 있으면 그 범위에서 **무작위로** 흩뿌린다(연사 무기용).
- `Shotgun` — 펠릿을 부채꼴에 **균등 배치**한다. 난수로 뿌리면 발마다 명중 수가 흔들려
  "운에 따라 세지는 무기"가 되고 DPS 기준선을 못 잡는다.
- `Rocket` — 착탄 시 `aoeRadius` 안 전체에 같은 피해. 직격 대상도 포함한다(§05 "착탄 반경 폭발").
- `Cone` — 투사체 없이 전방 부채꼴을 매 틱 직접 때리고 화상을 남긴다.
  화상은 **0.25초마다** 들어간다(매 프레임이면 프레임레이트가 피해량이 되고, 1초면 2초 화상이
  2번만 들어와 손실이 크다). 같은 적에 **겹쳐 쌓지 않고 지속시간만 갱신**한다 — 쌓이게 두면
  분사 한 번에 화상이 수십 겹 붙어 DPS 가 기획 수치와 무관해진다.
- `Orbit` / `Companion` — **주무기가 아니다.** 아래 보조 장비 절 참조.

## 보조 장비 (`ProtoSupportGear`)

회전 블레이드·지원 드론은 **레벨업 카드로 얻는 자동 공격 장치**다. 손에 쥐지도 조준하지도 않아
나머지 네 무기와 조작 감각이 다른 축에 있어서, 캐릭터에 고정하지 않고 누구나 붙일 수 있게 했다.

- **슬롯 상한 2** (`ProtoSupportGear.MaxSlots`). 상한이 없으면 결핍이 사라져 무기 4슬롯 시절로 되돌아간다.
  슬롯이 찬 뒤에는 **새 장비 카드가 후보에 아예 안 뜬다**(§07 "먹을 수 없는 카드를 보여주지 않는다").
  이미 가진 장비의 레벨업 카드는 계속 뜬다.
- 에셋은 주무기와 같은 `WeaponModelDef`(모델·배율) + `WeaponStats`(수치) 한 쌍이다. 동작은 이미
  그 안에 정의돼 있고 **얻는 경로만** 달라졌다. `ProtoRun.gearOrbitBlade/gearSupportDrone` 에 배선한다.
- 레벨 성장은 수식이 아니라 표(`levelCounts` / `levelDamageMult`)다 — "3레벨에 블레이드가 몇 개?"를
  코드를 읽지 않고 답할 수 있어야 한다. 현재 개수 `1,2,3,3,4` / 피해 배율 `1,1,1,1.5,1.5`.
- `Orbit` 은 궤도 루트의 월드 회전을 매 프레임 identity 로 고정한다. 안 그러면 주무기 조준 회전이
  궤도에 얹혀 블레이드가 순간이동하듯 튄다.
- `Companion` 은 소환물이 **자기 위치에서 따로 조준**한다. 투사체는 `ProtoShooter.FireExternal` 로
  **주무기 풀을 빌려 쓴다** — 풀을 컴포넌트마다 따로 두면 총알이 두 벌 생겨 상한 관리가 무의미해진다.
- 런 재시작 시 `ClearAll()` 로 지운다. 안 지우면 새 판에 지난 판 블레이드가 그대로 돈다.

확인 화면: `Assets/Screenshots/support_gear.png` (블레이드 3 + 드론 3).

## 경험치 젬 스프라이트 (임시)

`ProtoGemPool.gemSprites` 에 텍스처를 넣으면 큐브 대신 그림이 떨어진다. **배열을 비우면 기존
큐브 경로로 그대로 돌아간다** — 임시 테스트라 되돌리는 비용을 0으로 뒀다. 현재 물고기 3종
(`Art/1.png` 열대어=1XP, `2.png` 고등어=2XP, `3.png` 상어=보스). XP가 클수록 큰 물고기다.

- 카메라를 향해 세우는 **카드보드 빌보드**. 큐브처럼 Y축으로 돌리면 스프라이트가 옆면으로 사라진다.
  위상은 젬마다 흩뿌린다 — 안 그러면 줄지어 춤춘다.
- **알파 컷아웃**을 쓴다. 반투명이면 젬 수십 개가 겹칠 때 정렬이 흔들려 깜빡인다.

### 파닥거림 — 3D 모델도 스프라이트 시트도 쓰지 않았다

몸이 휘는 것은 **정점 변형 셰이더**(`Proto/GemFish`)가 한다. 그림 한 장을 가로 12칸으로 쪼갠
쿼드에 얹고 길이 방향으로 사인파를 넣으면 꼬리가 실제로 젓는다 — 아트 추가 0. 나무 바람
흔들림(`BCM_WIND_SWAY`)과 같은 방식이다. 카메라가 피치 58° 고정이라 여러 각도에서 볼 일이 없어
3D 모델은 회수가 안 되고, 픽업 하나에 드로우콜을 붙이는 것도 적 300마리 예산에서 아깝다.

- **쿼드를 쪼개는 것이 전부다.** 정점이 4개면 휘게 할 정점이 없어서 사각형이 통째로 기울 뿐이다.
- 머리(로컬 −x)는 고정하고 꼬리로 갈수록 크게 휜다. 가중치를 **제곱**으로 떨어뜨려야 머리가
  뻣뻣하게 남는다 — 선형이면 몸 전체가 흐물거린다.
- **메시 바운즈를 휨 진폭만큼 넉넉히 잡는다.** 안 그러면 크게 휠 때 프러스텀 컬링에 걸려 사라진다.

**상태를 셋으로 나눈 이유가 가독성이다.** 젬이 화면에 40개 넘게 깔리는데 전부 계속 파닥거리면
§15 의 "대비를 캐릭터에 몰아준다"가 깨져 플레이어를 못 찾는다.

| 상태 | 지속 | 회전 | 높이 | 셰이더 `_Flop` |
|---|---|---|---|---|
| 낙하·튕김 | ~0.7s | ±14° 느리게 | `TickFall` 이 소유 | 0 (공중) |
| 착지 파닥 | 0.40s (제곱 감쇠) | ±26° **속도 30** | 들썩임 0.045m | 1 → 0 |
| 정지 | 먹을 때까지 | ±2.5° | 호흡 0.02m | 0 |
| 자석 | 0.36s | ±11° | 고정 | 0 |

### 떨어지고 튕긴다

예전에는 좀비가 죽은 자리에 `y=0.35` 로 **툭 나타났다** — 떨어지는 과정이 없으니 파닥거림이
어디서 시작되는지도 안 읽혔다. 유니티 물리는 쓰지 않고(§16) 수직 속도만 적분한다.

- `restY + dropHeight`(0.95m)에서 위로 `dropUpSpeed`(1.2m/s) 튀며 시작 → 중력 20 → 두 번쯤 튕기고 정지.
- **튕길 때마다 `flopAt` 을 갱신해 파닥을 다시 터뜨린다.** 착지 충격과 파닥이 같은 순간에 나야
  "떨어져서 파닥거린다"로 읽힌다. 공중에서는 `_Flop = 0` 이다.
- 반동이 1.0m/s 밑이면 그만 튄다 — 안 그러면 바닥에서 미세하게 영원히 떤다.
- 높이의 주인이 상태에 따라 다르다: 공중 = `TickFall`, 바닥 = `TickSpriteLook`, 자석 = 자석 로직.
  두 곳에서 같이 쓰면 서로 덮어써서 젬이 바닥에 붙어 떨린다.
- **좀비 옆으로 튀어나간다.** 시체가 죽은 자리에 2.2초(`DeathLinger`) 남아 있어서 그 자리에
  떨어지면 젬이 통째로 가린다. 스폰 좌표를 옮기는 대신 **수평 속도**(`scatterSpeed` 2.0m/s)를
  줘서 궤적으로 빠져나오게 했다 — "저기서 나왔다"가 궤적으로 읽힌다. 실측 이동 거리 0.81~1.12m.
  방향은 무작위지만 **카메라 쪽(−Z)으로 치우친다**(`scatterCameraBias` 0.55) — 카메라가 −Z 에서
  내려다보므로 −Z 로 튀면 시체 *앞*에 떨어져 가리지 않는다. +Z 로 가면 시체 뒤라 아예 안 보인다.
- **착지할 때마다 수평 방향이 꺾인다**(`TurnOnBounce`, 80~200°). 한 방향으로만 호를 그리면
  "미끄러진다"로 보이는데, 파닥거리는 물고기는 앞으로 갔다 되돌아오고 옆으로 튄다.
  180° 근처가 걸리면 왔던 자리로 돌아가고 90° 근처면 옆으로 간다.
  **완전 무작위로 새 방향을 뽑지 않고 이전 방향에서 꺾는** 이유는, 무작위면 우연히 같은 방향이
  걸려 그냥 미끄러지는 착지가 섞이기 때문이다.
- **방향 반전이 이동 거리를 상쇄한다** — 이게 튜닝의 함정이다. 홉을 0.70 → 0.37m 로 잡았을 때
  최종 변위가 0.64m 밖에 안 남아 "제자리에서 떤다"로 보였다. **홉이 길어야 반전이 보인다.**
  거리를 좌우하는 것은 수평 속도만이 아니라 **체공 시간(= `bounciness`)** 이다 — 0.55 였을 때
  체공이 0.35 → 0.27 → 0.13s 로 급하게 줄어 두 번째 홉부터 거리가 안 나왔다.
  지금 값(`scatterSpeed` 3.2 / `friction` 0.8 / `bounciness` 0.65)의 홉 거리:
  **1.15 → 0.85 → 0.44 → 0.22 → 0.11 → 0.05m**, 총 경로 2.82m, 1.17초.
  실측 최종 변위 평균 **1.09m**(물고기 몸길이 0.42m 의 2.6배) — 이전 0.64m 에서 70% 늘었다.
- **수치가 약하면 아예 안 보인다.** 처음 `dropUpSpeed 1.2 / bounciness 0.42` 로 잡았더니 튕김이
  한 번 11cm, 0.2초여서 "변한 게 없다"는 소리를 들었다. 카메라가 17.76m 떨어져 있고 물고기가
  0.42m 라는 것을 계산에 넣어야 한다. 지금 값은 정점 1.23m, 첫 튕김 0.22m, 4회, 총 0.85초다.

> **함정 — 씬에 저장된 값이 코드 기본값을 덮는다.** `flopTiltSpeed` 기본값을 15 → 30 으로
> 올렸는데도 인게임은 그대로 15 였다. 이미 씬에 직렬화된 컴포넌트는 **새 기본값을 쓰지 않는다.**
> 튜닝 기본값을 바꿀 때는 씬 인스턴스도 같이 밀어줘야 한다(2026-09-08 에 실제로 밟았다).

- **자석 속도를 9 → 5 m/s 로 낮췄다.** 9 였을 때는 픽업 반경 1.8m 를 0.15초에 통과해서
  "물고기가 헤엄쳐 온다"가 눈에 보이지 않았다(진행 방향 반전은 프레임 사이에 끝나 관찰조차 못 했다).
- **알려진 비용**: 젬마다 다른 `_Flop`·`_Phase` 를 넣으려고 MPB 를 쓰는데, MPB 는 SRP Batcher 를
  끊는다 → 화면의 젬 개수만큼 드로우콜이 늘어난다(실측 46개까지 나왔다). 임시 테스트라 감수했다.
  본 게임으로 가져갈 때는 젬을 인스턴싱으로 묶고 파닥 세기를 인스턴스 데이터로 넘겨야 한다.

### 흡수될 때도 헤엄친다 (2026-09-18)

빨려 들어오는 동안 물고기가 **바닥에 붙은 채 통째로 미끄러졌다.** 원인 두 개였다.

1. 높이를 정하는 블록이 `if (!magnet && g.grounded)` 로 막혀 있어서 **끌려올 때 y 를 아무도
   안 건드렸다.** 자석 이동은 `to.y = 0` 이라 수평 성분만 더한다 — 그래서 높이가 그대로였다.
2. 셰이더의 몸 휨(`_Flop`)은 **착지 파닥**에서만 올라간다. 끌려올 때쯤이면 이미 사그라들어
   0 이라 몸이 안 휘었다.

고친 내용:

```
끌려오는 동안 y = lerp(걸린 순간 높이, baseY + magnetLift, smoothstep(경과/magnetLiftTime))
                + sin(t * magnetSwimSpeed + 위상) * magnetSwimAmplitude
_Flop = max(착지 파닥, magnetBend)
```

| | 흡수 전 | 흡수 중 |
|---|---|---|
| 높이 | baseY (0.35) | **+0.34m 떠올라 ±0.07m 로 위아래 헤엄** |
| 셰이더 `_Flop`(몸 휨) | 0.00 | **0.45** |
| 화면상 갸웃 각도 | 2.5° | **21.3°** |

`_Flop` 하나를 올리면 **몸 휨·갸웃 각도·갸웃 속도·스쿼시가 한꺼번에** 올라간다
(`tilt`/`speed`/`sq` 가 전부 flop 으로 보간된다). 그래서 자석 상태를 "계속되는 파닥"으로
취급하는 게 값 하나로 끝나는 가장 짧은 길이었다.

**걸린 순간의 높이에서 출발한다**(`magnetY0`). 공중에서 자석에 걸리는 경우가 있는데,
`baseY` 에서 시작하면 그 순간 물고기가 바닥으로 툭 떨어졌다가 다시 뜬다.

## 몸 회전 — 회전의 주인은 `ProtoPlayer` 다

예전에는 `ProtoShooter` 가 **발사할 때만** `transform.rotation` 을 직접 대입했다. 그래서
회전이 발사 간격만큼 뚝뚝 끊겼다 — 소총은 0.35초마다, **로켓은 1.7초에 한 번 툭** 돌았다.
게다가 사거리 안에 적이 없으면 아예 돌지 않아서, 걸어도 방향이 바뀌지 않았다.

- **조준 방향은 슈터가 매 프레임 알려주고**(`ProtoPlayer.SetAimDir`), **실제로 몸을 돌리는 것은
  이동을 소유한 `ProtoPlayer`** 가 한다. 회전과 이동이 다른 컴포넌트에 나뉘어 있으면 서로를 덮어쓴다.
- 보간은 `Quaternion.RotateTowards` + `ProtoConfig.TurnSpeed`(720°/s). 180° 반전이 0.25초다.
  프레임당 상한은 `TurnSpeed × MaxDeltaTime = 36°` 라 씬 로드 직후 긴 프레임에도 튀지 않는다.
- 조준 방향에 **유효 시간 0.2초**를 둔다. `Update` 실행 순서가 정해져 있지 않아서, 슈터가 이 프레임에
  먼저 돌든 나중에 돌든 결과가 같아야 한다.
- 사거리에 적이 없으면 **이동 방향**을 바라본다. 둘 다 없으면 현재 방향 유지.
- **화염 콘만 판정 방향이 `transform.forward`** 다. 콘 메시가 루트의 자식이라, 회전이 따라오는 동안
  조준 원본 방향으로 판정하면 그림과 판정이 어긋난다 — 부채꼴은 그게 눈에 바로 보인다.
  투사체는 총구를 떠나면 스스로 날아가므로 조준 방향을 그대로 쓴다.

> 실측(플레이 모드): 발사 간격 **1.7초인 로켓**으로도 몸 방향과 최근접 적 방향의 오차가 **0.4°**.

## 로켓 착탄 폭발 (`ProtoExplosion` + `Proto/Explosion`)

`ProtoProjectile.Explode()` 가 피해를 주기 전에 `ProtoExplosion.Play(center, aoeRadius)` 를 부른다.
**씬 배선이 필요 없는 정적 호출**이다(`ProtoLevelUpBeam` 과 같은 방식). 다만 빛기둥은 한 번에
하나뿐인데 폭발은 동시에 여러 개 터질 수 있어서(융단 폭격 진화는 6지점) **풀**을 둔다.

**네 겹**이고, 셰이더 하나가 `_Kind` 로 갈라 그린다. 겹마다 색·`_Lobe`·`_Alpha` 만 다른
머티리얼 4장을 굽고, 인스턴스마다 달라지는 `_Progress` · `_Seed` 만 MPB 로 넣는다.

| 겹 | 시작~종료 | 하는 일 | 왜 |
|---|---|---|---|
| 섬광 | 0.00~0.07 | 흰 원판, 크기 고정 | 첫 프레임의 열감. 예전엔 처음부터 연노랑이라 "뜨겁다"가 없었다 |
| 화구 | 0.00~0.30 | ease-out-back 으로 톡 튀었다 살짝 줄어든다 | 타격감. 커지기만 하면 "번지는 연기"로 보인다 |
| 지면 충격파 링 | 0.02~0.47 | 반경까지 `sqrt` 로 퍼지며 얇아진다 | **테두리가 정확히 판정 반경**이라 무엇이 맞았는지 읽힌다. 데미지 숫자를 안 쓰는 게임(§15)에서 그 정보가 여기밖에 없다 |
| 연기 | 0.10~1.00 | 부풀며 1.35m 올라간다 | 화구가 멈춘 뒤에도 움직이는 게 있어야 "끝났다"가 아니라 "지나갔다"로 읽힌다 |

> **지면 그을음 자국(5번째 겹)은 만들었다가 제거했다** — 도로가 어두워지는 게 보기 싫다는
> 판단이다. 다시 넣을 일이 생기면: 지면에 눕는 원판 + `1 - smoothstep(0.45, 1, p)` 알파,
> 높이는 링(`0.09`)보다 낮은 `0.07` 이 전부다. 대신 **폭발을 맞은 좀비가 검게 남는** 쪽으로
> 흔적을 옮겼다(아래 절).

### 왜 시간을 갈랐나

예전에는 **모든 겹이 0.34초 곡선 하나를 공유**했다. 같이 나타나 같이 사라지니 "터졌다 → 남았다"가
없이 평평하게 보였다. 지금은 `Local(age, delay, len)` 이 겹별 진행도를 따로 계산하고,
`Fx.age` 는 정규화 t 가 아니라 **초**를 센다. 총 수명은 가장 긴 겹(연기 **1.00s**)이 정한다.

> **함정 — MPB 는 블록 전체를 갈아끼운다.** `_mpb` 하나를 채워 두 렌더러에 `SetPropertyBlock`
> 하면 두 겹이 **같은 `_Progress`** 를 받는다. 이게 예전 구조가 시간을 공유하던 실제 이유다.
> 지금은 `Push()` 가 겹마다 `Clear()` → 다시 채운다.

### 실루엣 노이즈 (완벽한 원 깨기)

침식이 없을 때 화구는 동심원 밴드가 그려진 정원(正圓)이라 **"폭발"보다 "조준 표식"** 으로 읽혔다.
각도 노이즈 한 번이 이 인상을 가장 크게 바꾼다.

- 노이즈를 **단위원 위의 좌표**에서 뽑는다: `fbm(normalize(uv-0.5) * _NoiseScale + _Seed)`.
  `uv.x` 를 각도로 쓰면 0/1 경계에 **세로 금**이 생긴다.
- 침식은 **안쪽으로만** 한다 (`lobe = 1 - ns * _Lobe`). 밖으로 부풀리면 `r>1` 인 혹이
  메시 테두리에 잘려 직선으로 끊긴다.
- 그래서 겉보기 크기가 줄어든다 → `fireballScale` 을 0.85 → **1.05** 로 올려 보상했다.
  실측: 반경 2.4m 기준 지름 4.08m → **3.98m** (거의 동일).
- 실측 실루엣: 반경이 평균값 대비 **17~27%** 흔들리고 혹이 **5~9개** 생긴다. `_Seed` 를
  폭발마다 `Random*64` 로 주므로 두 발이 같은 모양으로 나오지 않는다.
- **링만 노이즈로 흐트리지 않는다.** 그 바깥 지름이 판정 반경 정보를 나르기 때문이다.
  밝기만 `lerp(1, ns, 0.3)` 으로 얼룩지게 한다.
- 원판 세그먼트를 40 → **64** 로 올렸다. 침식하면 다각형 테두리의 직선 구간이 혹의 곡선과
  겹쳐 보인다.

### 오버드로 방어

`detailBudget = 3`. **동시 폭발이 3개를 넘으면 이후 폭발은 화구+링 2겹만** 그린다.
융단 폭격은 2.2초마다 6지점을 동시에 때리므로, 막지 않으면 반투명 오버드로가 그 순간
몇 배로 곱해진다. 화구 하나가 이미 지름 3.98m ≈ 가시 폭 11m 의 36% 다.
값을 0 이하로 두면 안 된다(`Mathf.Max(1, detailBudget)` 로 막혀 있다).

- 원판 UV 규약은 `ProtoLevelUpBeam.BuildDisc` 와 같다 — `length(uv-0.5)*2` 가 테두리에서 1.
- 알파를 `(1-progress)²` 로 떨군다. 선형이면 옅은 원판이 오래 남아 지저분해진다.
- 지면에 눕는 겹은 링뿐이다. 높이 `0.09` — 도로 차선(0.00~0.05)과 Z파이팅이 나는 구간 위다.

> **함정 — 첫 프레임 빌보드.** 카메라를 `Apply` 안에서 처음 잡으면, 그 프레임의 화구가
> 회전 identity(XY 평면에 세로로 선 원판)로 그려진다. 피치 58° 카메라에서 그건
> **도로를 가로지르는 납작한 어두운 띠**로 보인다 — 진단 중에 실제로 본 증상이고, 화구가
> 고장난 것처럼 보여서 원인을 찾는 데 시간이 걸렸다. `PlayAt` 에서 카메라를 먼저 잡아 막았다.

### 폭발 그을음 — 맞은 좀비가 검게 남는다 (`ProtoZombie.ApplyBlastSoot`)

지면 자국을 지운 대신 **흔적을 좀비 쪽으로 옮겼다.** 폭발 반경에 든 좀비는 `_blasted` 가 서고
`BlastTint`(0.11)로 어두워진다. **화상과 달리 지속시간이 없다** — 한 번 붙으면 죽을 때까지 안 풀린다.

- `ProtoProjectile.Explode()` 가 **피해보다 먼저** 부른다. `TakeDamage` 안에서 죽으면 그 뒤에
  붙여도 사망 연출을 못 잡아서, 이 폭발로 죽는 좀비가 원래 색으로 쓰러진다.
- **그을린 좀비에 화상이 붙어도 `BurnTint`(0.62)로 밝아지지 않는다.** 그대로 두면 폭발 흔적이
  화염에 지워져 검정이 풀린 것처럼 보인다. 이 경우 알베도는 검정 유지, 이미션만 벌겋게 올린다.
- 우선순위: **화상 사망 연출(재) > 폭발 그을음 > 화상 > (이미션은 피격 플래시가 최우선)**.
- **피격 흰 플래시는 그대로 읽힌다** — 플래시는 `_EmissionColor`, 그을음은 `_BaseColor` 라
  서로를 지우지 않는다. 검은 몸에서도 맞은 게 보이는 유일한 이유다.
- `ResetVisual()` 이 `_blasted` 를 내린다. 안 내리면 **풀에서 재사용된 좀비가 검은 채로 등장**한다.

> **읽힘 주의.** 원래 이 파일의 화상 절에는 "**완전한 검정은 사망 연출에서만**" 이라고 적혀 있다 —
> 저채도 야간 배경(§15)에서 검은 좀비는 실루엣이 묻힌다는 이유였다. 그래서 `BlastTint` 를
> 재(`CharTint` 0.06)보다 밝은 **0.11** 로 뒀지만, 실기 화면에서 여러 마리가 검게 변한 뒤
> 무리가 배경에 묻히는지는 아직 확인하지 않았다. 묻히면 이 값만 올리면 된다.

## 화면 흔들림 (`ProtoCameraFollow.Shake`)

GDD §03 규정(v0.6, 2026-10-13 개정): **4단계, 진폭 상한 0.45m, 접근성 옵션에서 0.**
상한과 온/오프를 `ProtoCameraFollow` 가 들고 있다 — 부르는 쪽이 제각각 세게 흔들면
그 규정이 무의미해진다. 호출은 단계 API `ProtoCameraFollow.Shake(Impact)` 를 쓴다
(직접 값 `Shake(진폭, 길이)` 는 탱크 사격·착지 같은 예전 호출만).

| 단계 | 진폭/길이 | 쓰는 곳 |
|---|---|---|
| Light | 0.05m / 0.10s | 치명타 적중 |
| Medium | 0.14m / 0.25s | 로켓·융단 폭격, 포위 등장, 울타리 솟음, 플레이어 20 이상 피격 |
| Heavy | 0.28m / 0.40s | 보스 내려찍기, 최종 보스 등장, 탱크 파괴 |
| Huge | 0.42m / 0.60s | 보스 도약 착지, 승합차 폭발 |

- 예전 상한 0.12m 는 카메라 18m 거리에서 거의 안 보였다. 씬에 0.12 가 저장돼 있어 `Awake` 에서 0.45 로 끌어올린다.
- **탱크 공격은 흔들지 않는다**(2026-10-13): 사격 반동 호출 삭제, 포탄 착탄 폭발은 `WeaponStats.noShake` → `ProtoExplosion.Play(shake:false)`. 탱크 파괴(Heavy)·들이받기·파괴 연쇄 폭발은 그대로.
- `ProtoExplosion.shakePerRadius`/`shakeDuration` 은 단계화 이후 미사용(씬 직렬화 때문에 필드만 남김).
- **`_basePos` 를 따로 둔다.** 흔들림을 `transform.position` 에 직접 더하면 그게 다음 프레임
  `SmoothDamp` 의 입력이 되어 카메라가 흔들림만큼 계속 밀려난다.
- **화면 축(`transform.right` / `up`)으로만 흔든다.** 월드 XZ 로 흔들면 피치 58° 때문에
  세로 성분이 깊이로 새어나가 "카메라가 다가온다"로 보인다.
- 감쇠는 `k²`. 선형이면 끝이 질질 끌린다.
- **동시 폭발은 더하지 않는다.** 남은 흔들림보다 센 것만 받아 갈아탄다 — 6지점 융단 폭격에서
  진폭을 누적하면 화면이 뒤집힌다. 약한 게 강한 걸 끊지도 않는다.
- `Mathf.PerlinNoise` 는 정수 격자에서 항상 0.5 다. 축마다 다른 좌표로 뽑아야 한다.
- 보스 착지는 아직 이벤트가 없어서 호출하는 곳이 폭발뿐이다.

## 화염 — 파티클 전용 (`ProtoFlameCone` + `FX_FlameJet`)

Unity Particle Pack 의 `FlameThrower` 에서 화염·잉걸불만 떼어 `Resources/VFX/FX_FlameJet` 으로
만들고, `ProtoFlameCone` 이 그걸 무기 수치에 맞춰 구동한다.

### 절차적 부채꼴은 걷어냈다

예전에는 `Proto/FlameCone` 셰이더로 지면에 누운 부채꼴 메시를 구워 판정 범위를 그렸다.

- `Proto_FlameCone.shader` 와 `M_FlameCone.mat` 은 **지우지 않았지만 아무도 참조하지 않는다.**
  되돌리려면 `ProtoFlameCone` 의 히스토리를 보면 된다.
- `ProtoShooter.flameMaterial` 필드와 `ProtoSceneBuilder` 의 배선도 같이 없앴다.
  씬을 다시 저장하면 직렬화에서도 빠진다.

**대신 판정 범위를 보여줄 책임이 파티클로 넘어왔다.** 그래서 콘 전각을 깎지 않는다 —
깎으면 실제로는 맞는데 안 맞는 것처럼 보이는 가장자리가 생긴다.

### 수치는 무기에서 역산한다

팩 원본은 **1° 직선 제트에 10m**(바운즈 16m)였다. `ConfigureJet()` 이 `WeaponStats` 에서 다시 잡는다.

| 항목 | 계산 |
|---|---|
| 콘 각도 | `coneDegrees * 0.5` (Unity 는 **반각**) · 잉걸불만 ×0.85 |
| 속도 | `range / 수명` — 수명이 다할 때 딱 사거리 끝 |
| 입자 크기 | `range * 0.125` (불) / `range * 0.035` (잉걸불) |
| 방출량 | 340 (불) / 60 (잉걸불) |

밸런스가 사거리나 각도를 고치면 불이 자동으로 따라온다. 손으로 맞춘 값을 박아두면 반드시 어긋난다.

### `jetFlatten` — 이 값이 핵심이다

파티클 콘은 **입체**라 위아래로도 똑같이 퍼진다. 그대로 두면 **불이 도로를 뚫고 내려가**
노면 밑에서 불줄기가 삐져나온다(실측 로컬 y −0.63, 노면은 −0.36).

`scalingMode = Shape` + `localScale = (1, jetFlatten, 1)` 로 **모양만** 납작하게 누른다.
Shape 모드는 스케일을 입자 크기·속도에 안 걸기 때문에 **사거리는 그대로 두고 위아래 퍼짐만** 줄어든다.
(`Hierarchy` 로 두면 크기와 속도까지 눌려서 불이 쪼그라든다.)

실측 (사거리 4.5m / 전각 50° 기준, 노면 −0.36):

| flatten | y 최저 | z 최대 | \|x\| 최대 |
|---|---|---|---|
| 0.22 | −0.20 ✅ | 3.99m | 1.47m |
| **0.26 (기본)** | −0.24 ✅ | 3.78m | 1.48m |
| 0.34 | −0.51 ❌ 도로 관통 | 3.94m | 1.35m |

입자 **중심** 기준이라 스프라이트 반폭(약 0.28m)을 더하면 실제로 보이는 불은 약 4.3m x ±1.8m 다.
판정(4.5m x ±2.10m)보다 아주 조금 좁다 — 콘 가장자리로 나가는 입자가 드물기 때문이다.

### 세기 — 약해 보였던 이유 4가지 (2026-09-18)

"너무 약하다"의 원인은 파티클 수가 아니었다. 넷이 겹쳐 있었다.

| 원인 | 조치 |
|---|---|
| **블룸이 아예 없었다.** 씬 볼륨 프로파일 `Field_Look.asset` 이 **컴포넌트 0개**였다 | Bloom 추가 (threshold 0.90 / intensity 1.35 / scatter 0.72) |
| 불꽃이 **알파 블렌딩**(5/10)이라 빛을 더하지 않았다 | 머티리얼 사본 `M_FlameJet.mat` 을 **가법**(5/1)으로 |
| 입자 색이 **LDR 흰색**이라 블룸 임계값을 못 넘었다 | `startColor` 를 HDR (1.9, 1.9, 1.9) 로 |
| `sizeOverLifetime` 이 꺼져 있어 **뭉게뭉게 퍼지는 머리**가 없었다 | 0.35 → 1.0 커브 (총구는 가늘게, 끝은 부풀게) |

여기에 색 램프를 넣었다. 팩 원본 그라디언트는 흰색→흰색이나 마찬가지라 통째로 노란
덩어리로 보였다 — **불은 '온도 차'가 보여야 불로 읽힌다.**
백열(1,1,0.95) → 노랑(1,0.82,0.38) → 주황(1,0.45,0.10) → 적열(0.72,0.14,0.02).

> **블룸은 게임 전체에 걸리는 변경이다.** 불이 없는 화면을 켬/끔으로 비교한 결과 평균 차이
> 3.7/255, 흰 바리케이드·차선 가장자리만 아주 살짝 번진다 — 아트는 안 상했다. 다만
> **모바일 비용이 붙으므로** `highQualityFiltering` 은 꺼 뒀다. 번개도 같이 밝아진다(의도).

에셋스토어 레퍼런스 영상과 아직 다른 점:
- **모양.** 레퍼런스는 좁고 긴 제트를 옆에서 본 그림이다. 이 게임은 50° 부채꼴을 위에서 본다 —
  `coneDegrees` 를 바꾸지 않는 한 같은 실루엣은 안 나온다.
- **연기.** 레퍼런스의 검은 연기는 뺐다. 이 게임은 좀비가 보여야 한다.
- **성능 미검증.** 방출량 520/s + 가법 + 블룸이다. 기준 기기에서 재 본 적 없다.

### "불 여러 개"가 아니라 "불 하나"로 보이게 (2026-09-18)

밝기를 올리고 나니 이번엔 **알갱이가 하나하나 보이는** 문제가 남았다. 레퍼런스는 큰 덩어리가
서로 겹쳐 하나의 불로 보이는데, 작은 입자를 많이 뿌리면 반대가 된다.

레버는 셋이고, 영향력 순서대로다.

| 레버 | 바꾼 값 | 이유 |
|---|---|---|
| **입자 크기** | `range * 0.175` → `range * 0.32` (0.79m → **1.44m**) | 겹쳐야 하나로 보인다 |
| **수명** | `JetLife * 1.15` → `* 1.75` (0.39s → **0.60s**) | 동시에 살아 있는 입자가 늘어 더 겹친다. 속도가 `사거리/수명` 이라 **사거리는 그대로** |
| **방출량** | 520 → **170**/s | 크기를 키웠으니 수는 줄여야 한다. 안 줄이면 그냥 불바다 |

크기를 **2m 이상**으로 올리면 더 잘 뭉치지만 캐릭터를 덮고 콘 모양 자체가 사라진다 —
1.4m 근처가 균형점이다. 회전도 랜덤으로 돌려(`startRotation` 0~2π, `rotationOverLifetime`)
같은 스프라이트가 반복되는 티를 없앴다.

결과: 동시 입자 약 150개(이전 215개보다 적다), 도달 4.16m, 도로 관통 없음(y 최저 −0.27).

### 팩이 튜닝을 막던 것들 (전부 껐다)

| 모듈 | 문제 |
|---|---|
| `velocityOverLifetime` (space=**World**) | 플레이어가 돌아도 속도가 안 따라 돎 |
| `limitVelocity` (limit=0, damp=1.0) | 속도를 0 으로 눌러버림 — 잉걸불이 제자리에 멈춤 |
| `simulationSpace = World` | 불이 플레이어를 안 따라옴. **Local 이어야** 판정과 안 어긋난다 |
| `Smoke` (크기 10m) | 화면을 덮음 — 통째로 제거 |

**팩 프리팹은 루트 자체가 파티클이었다.** 모르고 루트를 지웠다가 불꽃이 통째로 빠지고
잉걸불만 남은 적이 있다. 부품을 뗄 때 루트를 먼저 확인할 것.

### 분사를 끊을 때

`emission.enabled` 만 여닫는다. `Stop()` 을 쓰면 이미 날아가던 불이 공중에서 통째로 사라진다 —
남은 불이 타서 꺼지는 게 맞다 (중단 0.25초 뒤 35개 잔류 확인).

### 팩 텍스처를 1024 로 낮췄다 (11MB 절감)

팩의 `Fireball` · `FireBallEmission` 이 **2048x2048** 이었다. 둘이 합쳐 14.6MB 다.
그런데 불꽃 텍스처는 **7x7 플립북**이고 입자 하나는 화면에서 약 155px(1080p)이다 —
1024 면 셀 하나가 146px 라 거의 딱 맞는다. 낮춘 뒤 2.4MB, 눈으로 차이가 안 보인다.

> **이건 팩 에셋의 임포트 설정이다. 팩을 다시 임포트하면 2048 로 되돌아간다.**
> 그때 조용히 11MB 가 다시 늘어나므로, 팩을 갱신하면 이 두 장을 다시 확인할 것.

발광 맵을 못 뺀 이유: `fireball.mat` 은 `_EMISSION` 이 켜져 있고 HDR 발광색(3.0, 0.97, 0.05)이
불의 광채를 만든다. 두 장 다 필요하다.

### 튜닝 손잡이 / 아직 안 한 것

`jetFlatten`(0.26), `JetLife`(0.34s 상수). 프리팹이 없으면 경고 한 줄만 남기고 판정만 돈다.

플레이 모드 실측은 안 했다. 위 수치는 에디터에서 `Configure()` 를 직접 호출하고
`ParticleSystem.Simulate()` 로 돌려 입자 좌표를 읽은 값이다.

## 비 (`ProtoRainFx`) — 옵션 3단계, 기본 **약함**

**빗줄기는 카메라 앞에 붙는 쿼드 한 장**이고, 바닥 튐만 파티클이다.

### 왜 파티클을 버렸나 — 측정이 답을 줬다

| 변형 | 기본 대비 | 입자 |
|---|---|---|
| 파티클 비 (rate 1100) | +0.230ms | 823 |
| 개수 절반 | +0.191ms | 442 |
| 개수 1/4 | **+0.104ms** | 253 |
| **크기 2배 (채우기 4배)** | **+0.226ms** | 809 |
| 크기 절반 | +0.226ms | 802 |

**크기를 키워 채우기를 4배로 해도 비용이 그대로**인데 **개수를 1/4 로 줄이면 55% 가 빠졌다.**
즉 비의 비용은 화면 채우기가 아니라 **입자 개수**였다 — 빌트인 파티클이 매 프레임 CPU 에서
정점을 새로 쓰기 때문이다(823개 = 정점 3,300개). 쿼드는 정점 4개고 시뮬레이션이 없다.

결과: **+0.230 → +0.125ms**, 입자 **823 → 54**.

> **세 연출의 성격이 각각 다르다.** 번개는 가지치는 고유 실루엣이 있어 플립북이어야 했고,
> 화염은 비용이 **채우기** 쪽이라 쿼드로 바꿔도 별로 안 싸지며, 비는 비용이 **개수** 쪽이라
> 쿼드가 정답이었다. "무겁다"만 보고 같은 처방을 내리면 안 된다 — **무엇이 비싼지부터 잰다.**

### 원경·근경은 쿼드 두 장이 아니라 한 패스의 두 샘플

두 장으로 만들면 채우기가 두 배가 되는데 모바일에서 진짜 위험한 게 그거다. 같은 픽셀에서
UV 만 다르게 두 번 읽으면 시차는 얻고 채우기는 한 장 값만 낸다 (`Proto/RainSheet`).

### 텍스처는 직접 구웠다 (`ArtSource/VFX/bake_rainsheet.py`)

팩의 `T_RainStreak`(32×128)은 **입자 하나에 붙이는 한 가닥**이라 세로 128행 중 126행이
채워져 있다. 그걸 타일링하면 끊김 없는 **세로 블라인드**가 되지 비가 안 된다.
`T_RainSheet`(512²)는 길이·굵기·농도가 제각각인 가닥 190개를 흩뿌리고 **가장자리를 wrap** 해
타일이 되게 구웠다. 타일 근경 2.6×1.6 / 원경 4.4×2.8 이 가장 자연스러웠다.

### 바닥 튐은 파티클로 남겼다

54개뿐이고, 비가 "바닥에 닿는다"는 느낌은 이쪽이 만든다 — 카메라 앞 쿼드로는 원리상 못 만든다.

### 팩 의존을 끊었다

`Assets/RainSnowCloudEffect` 를 참조하는 우리 에셋은 **0건**이다(튐 텍스처는 사본을 쓴다).
팩을 지워도 비는 그대로 동작한다.

### UV 부호 주의 — 비가 하늘로 솟았다

`uv.y` 를 **빼면 화면에서는 위로** 흐른다(텍스처 좌표와 화면 이동이 반대다). 처음에 빼놨다가
비가 거꾸로 올라갔다. 내려오게 하려면 **더한다**.

검증법: `Shader.SetGlobalVector("_Time", ...)` 로 시간을 직접 주입해 두 시점을 렌더하고,
**비 없는 렌더를 빼서 비 성분만 남긴 뒤** 세로 프로파일을 교차상관하면 이동량이 나온다.
배경째로 상관하면 정지한 도로에 끌려가 0 이 나오고, 원경·근경을 같이 켜면 두 속도가 섞여
값이 흐려진다 — `_FarWeight` 를 0 으로 두고 근경만 재야 한다.
실측 +46px(0.02초) / +97px(0.04초) = 아래로, 시간에 비례.

### 세기 3단계 (`ProtoSettings.RainLevel`)

옵션 창에서 **꺼짐 → 약함 → 강함** 순환. 기본값은 **약함**이다.

| | 시트 텍스처 | 가닥 | 농도 | 바닥 튐 |
|---|---|---|---|---|
| 약함 (가랑비) | `T_RainSheet_Light` | 52 | 0.55 | 67/s |
| 강함 (폭우) | `T_RainSheet` | 190 | 0.75 | 240/s |

**불투명도만 낮추면 '옅은 폭우'가 되지 가랑비가 안 된다.** 가닥 수·길이·굵기가 다른
텍스처를 따로 굽는다 — `bake_rainsheet.py` 의 `PRESETS` 에 둘 다 들어 있고 시드가 고정이라
다시 돌려도 같은 그림이 나온다.

빗줄기가 쿼드 한 장이라 **세기를 바꿔도 비용은 거의 그대로다**(텍스처와 농도만 다르다).

`M_RainSheet` / `M_RainSheet_Light` 의 `_Opacity` · `_NearTile`/`_FarTile` · `_Slant`(기울기) ·

`lightSplashScale`(0.28). 가닥 수를 바꾸려면 `bake_rainsheet.py` 의 `PRESETS` 를 고쳐 다시 굽는다.

- 확인: 임시 프로젝트 TffRainProbe(실제 `ProtoRainFx` 를 편집 모드에서 돌리고 파티클은 `Simulate`, 설정은 대역 `ProtoSettings`). 게임 화면·밤 어둠 막 위로는 미확인.
- **바닥 고리 은은하게**(같은 날, 사용자: "비올때 바닥이 너무 인위적으로 튀는것같아서 좀 은은하게"): 또렷한 흰 고리(알파 0.85, 가는 테) → 알파 0.35 · 테가 번진 흐린 고리 · 지름 0.3~0.55m · 0.4~0.6초 · 강한 비 140개/초.

## 불타는 좀비 몸 (`ProtoBurnFx`) — 옵션

화염에 타는 좀비 몸에 불 입자를 붙인다. **옵션 `ProtoSettings.BurningBodies` 로 끌 수 있다**
(옵션 창 세 번째 줄). 꺼도 그을린 색과 이미션은 남는다 — 무엇이 타는 중인지는 게임플레이
정보라 끌 수 있으면 안 된다. 그쪽은 `ProtoZombie.PushVisual` 이 쥐고 있고 이 클래스와 무관하다.

### ParticleSystem 하나가 전부를 담당한다

동시 생존 상한이 **90마리**(`BudgetCap`)다. 좀비마다 시스템을 달면 시뮬레이션 90개 +
드로우콜 90개가 된다. 여기서는 시스템 하나에 `Emit(EmitParams)` 으로 좌표를 직접 찍는다 —
**좀비가 몇 마리든 드로우콜 1개**다. 실측: 좀비 16마리 / 입자 273개 / 드로우콜 1.

화면 채우기는 걱정거리가 아니었다. 같은 잣대로 재면:

| | 입자 크기 | 12m 거리 | 개수 | 화면 채움 |
|---|---|---|---|---|
| 화염방사기 제트 | 1.44m | 169px | 150 | **약 1.6 화면** |
| 몸 불 | 0.46m | 54px | 12마리×3 | **0.02 화면** |

**이미 쓰고 있는 제트가 80배 비싸다.** 진짜 비용은 CPU(시스템 개수)였고 그래서 하나로 합쳤다.

### 밟은 함정 셋

1. **입자를 몸 중심에 뿌리면 안 보인다.** 메시 안쪽에서 생겨 깊이 테스트에 걸린다
   (가법이라 ZWrite 는 꺼져 있지만 ZTest 는 살아 있다). `ringInner`~`ringOuter`(0.30~0.46m)
   링에 뿌려 실루엣에 걸치게 한다.
2. **`AddComponent<ParticleSystem>()` 로 만든 시스템은 플립북이 안 나온다.** 불꽃 텍스처가
   7×7 플립북인데 새 시스템에는 `textureSheetAnimation` 도, 머티리얼의 `_FLIPBOOKBLENDING_ON`
   이 요구하는 **정점 스트림(UV2/AnimBlend)** 도 없다 — 화면에 **아무것도** 안 나온다.
   그래서 프리팹은 **화염 제트의 Flame 시스템을 복사해서** 만들었다(TSA 7×7, 스트림 5개).
   파티클이 **자식**에 있으므로 `GetComponentInChildren` 으로 잡아야 한다.
3. **방출량의 소수점을 버리면 불이 아예 안 보인다.** 60fps 에서 마리당 프레임당 0.43알이라
   반올림하면 전부 0 이 된다. `_carry` 로 소수점을 다음 프레임에 넘긴다.

### 튜닝 손잡이

`particlesPerSecond`(26) · `maxBurningShown`(12) · `cullDistance`(26m) · `bodyLow/High` ·
`ringInner/Outer`. 상한을 넘으면 거리 컷 후 **선착순**으로 자른다 — 90마리를 매 프레임
정렬하면 이 클래스를 만든 이유가 없어진다(불타는 좀비는 어차피 플레이어 앞에 몰려 있다).

밝기는 `M_BurnBody.mat`(화염 제트 머티리얼의 사본)에서. **블룸이 켜져 있으므로** 제트보다
어둡게 잡아 뒀다 — 여러 마리가 동시에 타면 화면이 하얗게 뜬다.

### 아직 안 한 것

플레이 모드 실측은 안 했다. 위 수치는 에디터에서 가짜 디렉터에 좀비를 꽂고
`LateUpdate` 를 직접 돌려 잰 값이다. **실기기 측정도 여전히 없다.**

## 화상 표시 — 좀비를 그을리게 (`ProtoZombie`)

**화상은 적의 상태로 `ProtoZombie` 가 들고 있다.** 슈터가 목록으로 들고 있으면 무기를 바꾸는 순간
사라지고, 파이로의 '불씨'(화상 적 처치 시 전파, §06)가 붙을 데도 없어진다.

표시는 **두 프로퍼티를 같이** 쓴다.

| 상태 | `_BaseColor` (알베도 곱) | `_EmissionColor` (가산) |
|---|---|---|
| 평상시 | 흰색 | 검정 |
| 화상 중 | `0.62` 그을림 | 낮은 주황 — 속이 벌겋게 |
| 피격 플래시 | *(그대로)* | 흰색 1.5 |
| 화상으로 사망 | 0.55초에 걸쳐 `0.06` 재 | 0 으로 소멸 |

- **왜 살아 있는 동안은 완전한 검정이 아닌가.** §15가 환경을 저채도 야간으로 깔았고 좀비는
  푸른 회색이다. 여기서 새까맣게 만들면 상태 표시가 배경에 묻혀 목적과 반대로 간다.
  무엇보다 파이로는 *어느 좀비가 타고 있는지* 읽어야 패시브를 굴릴 수 있다.
  완전한 검정은 **화상 사망 연출에서만** 쓴다 — 어차피 사라질 것이라 대비 손실이 누적되지 않는다.
- **왜 알베도인가.** 이미션은 더하기만 하므로 어둡게 못 만든다. 그리고 **프로퍼티가 달라야**
  피격 흰 플래시와 서로를 지우지 않는다 — 그을린 좀비가 총 맞으면 알베도는 그대로고
  이미션만 잠깐 하얘진다. 우선순위 중재 로직이 통째로 필요 없어진다.
- **함정**: `SetPropertyBlock` 은 블록을 **통째로** 갈아끼운다. 한쪽 값만 쓰는 경로를 만들면
  다른 쪽이 조용히 지워진다. 그래서 쓰는 곳은 `PushVisual()` **하나뿐**이고 항상 두 값을 같이 쓴다.
  마지막으로 밀어 넣은 값과 같으면 건너뛴다 — 300마리 × 렌더러 수만큼 매 프레임 부르면
  그것만으로 예산을 먹는다.
- 화상 피해는 **플래시도 넉백도 일으키지 않는다**(`DealDamage(amount, flash:false, zero)`).
  0.25초마다 하얘지면 "타고 있다"가 안 읽히고, 0.25초마다 밀면 좀비가 계속 떨린다.

확인 화면: `Assets/Screenshots/flame_cone.png`

### 모델 축 보정 (`modelRotationOffset`)

블렌더에서 뽑은 모델의 앞/위 축은 우리가 정하지 못한다. 그래서 코드에 각도를 박지 않고 데이터로 둔다.
**실측값**: 블레이드는 디스크 법선이 `+Z`(세워진 상태)라 `(90, 0, 0)` 으로 눕힌다.
드론은 코가 `+X`, 얇은 축이 `+Z` 라 `(-90, -90, 0)` 이어야 코가 앞을 보면서 수평으로 눕는다
(`Y -90` 만 주면 세로로 선 채 날아간다).

### 밟은 함정 2개 (둘 다 `Destroy` 지연 때문)

1. 캐릭터를 바꿔도 **무기 수치가 이전 것으로 남았다.** `Destroy` 는 프레임 끝에 실행되는데
   `RebindVisual` 의 `GetComponentInChildren<WeaponSocket>(true)` 가 아직 자식으로 남아 있는
   옛 소켓을 먼저 잡았다. 비활성으로 만들어도 `includeInactive=true` 라 찾힌다 —
   **부모에서 떼어내야** 한다.
2. 같은 이유로 이전 무기의 블레이드·드론이 한 프레임 남았다. `DetachAndDestroy` 로 통일했다.

무기 적용은 `Update` 를 기다리지 않고 `RebindVisual` 에서 **즉시** 한다. 다음 프레임으로 미루면
"교체했는데 블레이드가 없다"가 타이밍에 따라 달라져 재현이 안 된다.

## 휠로 카메라 각도 전환 (임시)

인스펙터에서 `preset` 을 바꿔 가며 보면 플레이 모드를 들락거리게 되어 감이 끊긴다.
플레이 중에 **마우스 휠**을 굴리면 각도 1 → 2 → 3 이 차례로 바로 갈린다
(`ProtoCameraFollow.TickPresetScroll()`). 각도 3 은 화각도 같이 바뀐다(42° ↔ 60°).

- **각도 값 자체는 안 건드린다.** 두 구도를 나란히 비교하는 게 목적이라, 굴릴 때마다
  숫자가 변하면 오히려 비교가 안 된다. `pitch`·`distance`·`angle2*` 는 그대로다.
- 휠 방향대로 순환한다(`System.Enum.GetValues` 로 돈다 — 각도가 늘어도 그대로 동작한다).
- 바꿀 때마다 화면 구석에 1.6초간 표시하고 콘솔에도 찍는다.
- 휠 한 번이 여러 프레임으로 들어오는 환경이 있어 0.12초 쿨다운을 뒀다 — 없으면 두 칸 넘어간다.
- **에디터·개발 빌드에서만 돈다** (`#if UNITY_EDITOR || DEVELOPMENT_BUILD`).
  `scrollSwitchesPreset` 을 끄면 휠을 완전히 무시한다. 휠은 이 프로젝트에서 다른 데 안 쓴다.

> **플레이 모드를 나가면 `preset` 도 되돌아간다**(유니티가 컴포넌트를 원상복구한다).
> 마음에 드는 쪽이 정해지면 인스펙터에서 같은 값으로 바꿔 둬야 한다 — 바꿀 때마다
> 콘솔에 찍히므로 나가서 그대로 보면 된다.

구도를 확정하면 `TickPresetScroll`·`OnGUI` 와 관련 필드를 통째로 지우면 된다.

    위 6.1m · 아래 0.1m · 좌우 3.3m 였고(각도 1 은 위 2.9 · 아래 0.3 · 좌우 2.9), 지금은 위쪽이 더 비칠 것이다.

그때는 위치·회전이 `smoothTime`(0.143s)으로 부드럽게 넘어간다.

## 화염방사기 연료 (파이로 — `WeaponStats.fuelSeconds`)

연속 분사에 상한을 두고, 다 쓰면 강제로 쉰다. 수치는 무기 에셋에 있다(§05 규약):

| 필드 | 값 (WS_Flamethrower) | 뜻 |
|---|---|---|
| `fuelSeconds` | 3.0 | 연속 분사 가능 시간. **0 이면 연료 제한 없음** — 다른 무기는 전부 0 이다 |
| `refuelSeconds` | 2.0 | 바닥나면 강제로 쉬는 시간. 끝나면 가득 찬다 |
| `fuelRegenPerSecond` | 0.8 | 분사하지 않는 동안 초당 회복 |

**이 게임은 사격이 완전 자동이다(§03).** 플레이어가 방아쇠를 놓을 수 없으므로 연료를
아끼는 유일한 수단은 **적에게서 떨어지는 것**이다. 즉 이 수치는 "얼마나 오래 붙어 있을 수
있는가 / 얼마나 자주 물러나야 하는가" 를 정하고, 파이로에게만 '붙었다 떨어졌다' 리듬을
강제한다. 회복(`fuelRegenPerSecond`)을 둔 이유가 여기 있다 — 회복이 없으면 교전이 이어질 때
연료가 조금씩 줄다가 엉뚱한 순간에 잠기고, 플레이어가 할 수 있는 일이 없다.

**부분 회복으로는 잠금이 풀리지 않는다.** 바닥나자마자 조금 회복해서 찔끔 쏘고 다시 잠기면
화염이 딸꾹질하는 것처럼 된다. 잠금은 시간으로만 풀리고, 풀릴 때 가득 찬다.

상태(`_fuel`·`_lockUntil`)는 **`ProtoShooter` 가 들고 있다.** 무기 에셋은 여러 캐릭터가
공유하는 수치라, 남은 연료를 거기 적으면 파이로가 쓰던 잔량이 다음 판까지 따라온다.
무기를 바꾸면 가득 찬 상태로 시작한다(`ApplyWeapon`).

잠긴 동안에는 **판정·이펙트·소리가 모두 멈춘다** — `ProtoShooter.Update` 가 `fueled` 로
한 번에 막고, 화염 콘은 `Pulse()` 가 안 불려 저절로 사그라들고, 루프 사운드도 꺼진다.

HUD 는 체력 바 아래에 연료 게이지를 그린다(`ProtoShooter.UsesFuel` 이 true 일 때만).
잠긴 동안에는 **바가 비는 게 아니라 파란색으로 차오르고** 남은 초를 같이 띄운다 —
비어 있기만 하면 "언제 다시 쏘는지" 를 알 수 없다.

## 효과음 (`ProtoAudio`)

클립 44개 / 키 22종. **씬 배선이 필요 없다** — `ProtoAudio.Play()` 를 처음 부르면 자기
GameObject 를 만들어 붙는다(`ProtoLevelUpBeam`·`ProtoExplosion` 과 같은 방식).

```
ProtoAudio.Play("hit", pos)          // 월드 위치 — 거리로 음량·좌우가 정해진다
ProtoAudio.Play2D("levelup")         // 화면 전체에 속하는 소리 (거리 감쇠 없음)
ProtoAudio.PlayLadder("gem", pos)    // 연속 호출 시 음이 한 단씩 올라간다
ProtoAudio.SetLoop("flame_loop", on) // 지속음 (페이드 인/아웃)
ProtoAudio.StopAll()                 // 런 종료·재시작
```

**키와 변형**: `Assets/_Game/Resources/SFX` 의 파일명에서 뒤의 `_숫자` 를 떼면 키가 된다
(`hit_1 hit_2 hit_3` → 키 `hit`). 재생마다 직전과 다른 변형을 고른다. 파일을 추가하면
코드를 고치지 않아도 변형이 늘어난다.

**왜 AudioSource 를 오브젝트마다 달지 않는가** — 좀비가 260마리까지 살아 있고 초당 수십 번
탄착 판정이 난다. 개체마다 달면 같은 프레임에 40발이 맞을 때 40개가 동시에 울려 찌그러진다.
보이스 24개를 돌려쓰고, 소리마다 최소 간격·동시 발음 수를 `ProtoAudio.Policies` 표로
제한한다. **그 표가 곧 이 게임의 믹스 설계다.**

**왜 3D 사운드가 아닌가** — 카메라 피치 58° 구도에서 화면에 들어오는 지면은 15.3~25.0m 띠뿐이다.
Unity 3D 감쇠는 리스너 기준 구면이라 이 구도에서는 화면 안에 있는 소리가 거리 때문에 작아진다.
전부 2D 로 재생하고 **플레이어와의 수평 거리**로만 음량·좌우를 계산한다 — "화면에 보이면
들린다"가 보장된다.

**타이머는 전부 `Time.unscaledTime`** 이다. 레벨업 카드와 옵션 창이 `timeScale` 을 0 으로
내리므로(§07) `Time.time` 을 쓰면 그 화면에서 UI 클릭음이 한 번 난 뒤 영영 막힌다.

### 신음 앰비언스가 배경음처럼 들리던 문제 (2026-09-17 수정)

주변에 좀비가 없는데도 신음이 1초에 한 번꼴로 계속 나서 배경음처럼 들렸다. 세 군데가 겹쳤다.

1. **거리 조건이 없었다.** 필드 전체에서 무작위 6마리를 뽑아 그중 가까운 놈을 울렸다.
   좀비는 시야 밖 스폰 링(15~25m)에 항상 남아 있으므로 **후보가 떨어지는 일이 없었다.**
   → 반경 `GroanRadius`(11m) 안에 실제로 있는 놈만 세고, 0이면 재생하지 않는다.
   반경 안에서 reservoir sampling 으로 무작위 한 마리를 고른다 — 늘 최근접을 고르면
   신음이 같은 방향에서만 나서 포위된 느낌이 안 난다.
2. **빈도가 전체 생존 수 기준이었다.** 25마리만 살아 있어도 0.64초마다 울렸다.
   → 반경 안 마리 수 기준 `7.0 / sqrt(near)`, 1.6~5.0초로 묶는다.
   **신음 빈도를 만지는 자리는 이 한 줄뿐이다.**
3. **거리 감쇠 곡선이 반대였다.** `1 - t²` 로 써 놨었는데 그건 가까운 쪽이 평평하고 먼 쪽에서만
   급락하는 곡선이라 15m 에서도 음량이 83% 로 남았다 — 시야 밖 소리가 전부 가까이 들렸다.
   → `(1-t)²`. 이 수정은 신음뿐 아니라 **모든 위치 기반 소리**에 적용된다.

### 몬스터 소리가 거리와 상관없이 다 크게 들리던 문제 (2026-09-17 수정)

곡선을 고친 뒤에도 "다 크게 들린다"가 남아 있었다. 곡선이 아니라 **감쇠가 시작되는 지점**이
문제였다 — `NearRadius` 가 6m 라 그 안쪽은 감쇠가 0 인데, 좀비는 실측상 0~11m 에 몰려 있어
(5m 안 4마리 · 5~11m 11마리) **몬스터 소리 대부분이 감쇠 구간에 들어가지도 않았다.**
필드 좀비 26마리의 평균 음량이 **95%** 였다. 사실상 전부 최대 음량이다.

`NearRadius` 6 → **2.5m**, `FarRadius` 28 → **20m** 으로 바꿨다. 접촉 사거리가
0.85m(`EnemyDef.contactRange`)이므로 **붙어서 때리는 좀비는 그대로 원본 음량**이다.
같은 판에서 다시 재면 평균 **44%**, 아래 표대로 거리가 읽힌다 (플레이 모드 실측 = 이론값):

| 거리 | 1m | 2.5m | 5m | 8m | 11m | 15m | 19m+ |
|---|---|---|---|---|---|---|---|
| 음량 | 100% | 100% | 73% | 47% | 26% | 8% | 재생 안 함 |

`Policy.carry` 는 **이 소리가 닿는 거리의 배율**이다(`FarRadius` 에 곱한다). 폭발만 1.7 로
두었다 — 로켓 사거리가 11m 라 기본 곡선이면 최대 사거리 착탄이 26% 로 떨어져 남의 일처럼
들린다. 1.7 이면 같은 11m 에서 53% 다. 좌우(pan)는 `carry` 와 무관하게 언제나 `FarRadius`
기준이다: 폭발만 좌우가 덜 벌어지면 같은 자리에서 난 소리인데 방향이 달라 들린다.

총성·발소리·젬은 전부 플레이어 몸에서 1~2m 안에 나므로 이 변경의 영향을 받지 않는다.

### 치명타 소리가 튀던 문제 (2026-09-17 수정)

`crit` 이 "다른 악기" 처럼 들린다는 지적을 받았다. 재 보니 원인이 분명했다.

| | 400Hz 위 | tonal(순음성) |
|---|---|---|
| 총성 `rifle_1` | 35.7% | 98 |
| 고치기 전 `hit_1` | **0.8%** | **427** |
| 고치기 전 `crit` | 12.7% (대부분 핑 하나) | 338 |

탄착음이 거의 순음짜리 저역 덩어리였고, 치명타는 **그 위에 2100/3170Hz 사인 핑을 얹은 것**이었다.
나머지 대역이 비어 있으니 핑만 동떨어져 들렸다. 총성·젬에서 겪은 것과 같은 실수다.

지금은 탄착·치명타 모두 **총성과 같은 기계**(5 대역 레이어 + `balance()`)로 만든다.
치명타는 악기를 바꾸지 않고 같은 구조에서 중·고역 비중만 13% → 23% 로 올리고 40ms 길게 운다.

| | 20-120 | 120-400 | 400-1.2k | 1.2-4k | 4-12k | tonal |
|---|---|---|---|---|---|---|
| `hit_1` | 35.1% | 33.8% | 19.1% | 11.1% | 2.5% | 119 |
| `crit` | 22.2% | 27.7% | 21.4% | 20.6% | 6.1% | 75 |

`ArtSource/SFX/preview/burst_hit_crit.wav` 로 탄착 사이에 치명타가 섞이는 것을 들어볼 수 있다
(4번째·7번째가 crit). **치명타를 아예 없애려면** `ProtoZombie.DealDamage` 의
`Play(crit ? "crit" : "hit", ...)` 를 `Play("hit", ...)` 로 바꾸면 된다 — 한 줄이다.

### 음량

상대 음량은 **파형에 구워져 있다** (`ArtSource/SFX/tools/synth.py` 의 목표 피크 표).
코드에는 전체 음량 하나(`ProtoSettings.SfxVolume`, 옵션 창 슬라이더, 기본 0.8)만 있다.
두 군데서 음량을 만지면 어느 쪽이 기준인지 알 수 없게 되므로 **볼륨 수정은 synth.py 에서 한다.**

### 파형은 스크립트가 소유한다

wav 는 손으로 만든 것이 아니라 `ArtSource/SFX/tools/` 가 생성한 결과물이다. 고칠 때는 wav 가
아니라 도구를 고치고 다시 돌린다. 사용법·프롬프트 함정·버린 생성물은 `ArtSource/SFX/README.md`.

들어보려면 메뉴 **좀비 오버런 ▸ 효과음 들어보기** (플레이 모드에 들어가지 않아도 된다).

### 함정 3개

1. **탕탕 캐논은 발사 간격이 0.08초다**(초당 12.5발). 클립이 150ms 를 넘으면 보이스 상한에
   밀려 연사가 뚝뚝 끊긴다. 처음 420ms 로 만들었다가 겪었다 — 소총과의 구분은 길이가 아니라
   저역의 무게로 준다.
2. **Vorbis 를 쓰면 안 된다.** 인코더 패딩이 `flame_loop` 의 crossfade 이음새를 되살려
   한 바퀴마다 딸깍거린다. `SfxImportSettings.cs`(AssetPostprocessor)가 PCM +
   Decompress on Load 를 강제하므로 손으로 찍을 필요는 없다.
3. **씬에 AudioListener 가 없었다.** 증상이 "코드는 다 도는데 소리만 없음" 이라 찾기 어렵다.
   Main Camera 에 붙여 저장했고, `ProtoAudio.EnsureListener` 가 없으면 붙이는 안전망을 둔다.

## 발밑 링 (`ProtoGroundRing`)

메시를 코드로 생성한다(annulus, 96 tris) — 텍스처도 프리팹도 없다.

| 상태 | 색 |
|---|---|
| 평상시 | 초록 |
| 피격 직후(무적 프레임 0.6초) | 적색 점멸 14Hz |
| 체력 30% 이하 | 주황 맥동 |

**핵심은 셰이더다.** `Assets/_Game/Art/Shaders/Proto_OverlayUnlit.shader` 는
`ZTest Always` + `Queue=Overlay` 로 깊이 테스트를 무시한다. URP 기본 셰이더는 ZTest 를
노출하지 않아서 전용 셰이더가 필요했다.

### 렌더 큐 — 링이 캐릭터를 덮지 않게

`ZTest Always` 만 걸면 링이 좀비뿐 아니라 **캐릭터까지 덮는다.** 렌더 큐로 순서를 갈라 해결했다:

| 순서 | 대상 | 큐 |
|---|---|---|
| 1 | 좀비·프롭 (일반 지오메트리) | 2000 |
| 2 | **링** (ZTest Always) | 4000 |
| 3 | **캐릭터 + 무기** | 4001 |

캐릭터는 큐만 올라갔을 뿐 계속 일반 깊이 테스트(LEqual)를 하므로, **앞에 선 좀비에는 정상적으로
가려진다.** 오클루전이 깨지지 않는다.

`ProtoGroundRing.RaisePlayerQueue()` 가 `r.materials`(인스턴스 사본)의 `renderQueue` 를 올린다 —
프로젝트의 공유 머티리얼 에셋(`face 1.mat` 등)은 건드리지 않는다.

이 처리는 **`Awake` 가 아니라 `Start` 에서 해야 한다.** `WeaponSocket` 이 Awake 에서 무기를
생성하므로 Awake 시점에는 무기 렌더러가 없고, 그러면 무기만 큐 2000 에 남아 링에 덮인다.

끄려면 `drawPlayerAboveRing = false`.

> **2026-11-12 — 나무·덤불·풀은 줄기만 막는다** (사용자: "식물의 줄기랑 나무의 중앙(가지)만 막고 나머지는 통과").
> 잎 카드(알파 컷아웃 머티리얼)는 막지 않는다. `_Props` 안이든 밖이든 같다.
> - 나무(줄기 머티리얼이 따로 있는 잎 카드 나무 4종): 줄기·가지 면 중 무릎~가슴 높이(`setpieceSlab`)만 0.2m 칸으로 찍는다 — 줄기 둘레 약 0.4~0.6m.
>   가지가 갈라지는 높이(1.5m 위)는 지나간다. 나무 FBX 4종의 Read/Write 를 켰다(꺼져 있으면 가운데 `plantStemSize` 사각형).
> - 잎 카드뿐인 덤불·풀: 줄기도 잎 텍스처에 그려져 있어 면으로는 못 가른다 — 밑동 가운데 `plantStemSize`(0.3m) 사각형만.
>   키가 `setpieceMinHeight`(0.6m)보다 낮은 풀(Plant_B)은 막지 않는다.
> - 잎 카드가 없는 예전 침엽수(`Tree_Conifer.obj`, 필드 씬)는 그대로 전체 크기의 0.32배 사각형.
> 같은 날 회전 규약도 바로잡았다 — `Resolve`·`ProtoDestructibles`(발자국 경로)·`PropOverlapFixer` 가 박스 x 축을 (cos, sin) 으로 잡아
> 비스듬한 프롭·블로커의 판정이 실제 모습과 반대로 돌아가 있었다. 이제 전부 유니티 Euler Y 규약(x 축 = (cos, -sin))이다.

Unity Physics 를 쓰지 않는다 (GDD §16). 씬의 `_Props` 계층을 훑어 프롭 인스턴스마다
**XZ 평면 OBB(Y축 회전 사각형)** 를 만들고, 이동 목표 위치가 박스 안이면 침투가 가장 얕은
축으로 밀어낸다 → 벽을 따라 미끄러지는 움직임이 자연스럽게 나온다.

프롭이 랜덤 Y회전을 갖기 때문에 원형 근사보다 회전 사각형이 실제 실루엣에 훨씬 가깝다.

프롭별 충돌 크기 배율(`ProtoObstacles.Shrink`):

| 프롭 | 배율 | 비고 |
|---|---:|---|
| Van_Abandoned / Barrier_Concrete | 0.90 | |
| Barricade_Wood / Fence_Plank | 0.85 | |
| Barrel_Rusty | 0.80 | |
| Rubble_Concrete | 0.70 | 낮은 잔해라 관대하게 |
| **Tree_Conifer** | **0.32** | 수관(잎)이 아니라 **줄기만** 막는다 |

`blockEnemies` 를 끄면 적은 프롭을 통과한다. 뱀서류는 보통 적을 통과시켜 AI 가 끼는 문제를
피하는데, 여기서는 기본값 ON 이다 — 좀비가 밴을 뚫는 모습이 어색하기 때문. 좀비가 지형에
갇히는 현상이 보이면 이 토글을 먼저 끄고 확인할 것.

## 좀비 피격 피드백 (흰 플래시 + 넉백)

GDD §15가 데미지 숫자를 최소화하라고 했으므로 **숫자는 띄우지 않는다.** 대신 두 가지로 알린다.

| 값 (`ProtoConfig`) | 기본 | 비고 |
|---|---:|---|
| `HitFlashTime` | 0.09s | 더 길면 물량전에서 화면이 하얗게 뒤덮인다 |
| `HitFlashStrength` | 1.5 | `_EmissionColor` 값. 1.5면 거의 순백 (실측 RGB 0.966/0.967/0.969) |
| `KnockbackDist` | 0.16m | 총알 한 발에 밀리는 거리 |
| `KnockbackTime` | 0.11s | 선형 감쇠 |
| `EnemyDef.knockback` | 1 (보스 0.12, 엘리트 0.3) | 적마다의 배율 — 적 에셋 칸. 보스는 0.019m, 거의 안 밀린다 |

### 흰 플래시를 왜 이 방식으로 하나

**`_EmissionColor` 를 `MaterialPropertyBlock` 으로 흔든다.** 다른 방법을 두 번 시도했다가 접었다:

1. **머티리얼을 흰색으로 갈아끼우기** — 같은 머티리얼이 **발밑 블롭 그림자**(`_UsePlanarShadow`)도
   그리기 때문에, 갈아끼우는 순간 그림자가 같이 사라져 툭 튄다.
2. **`_BaseColor` 를 크게 곱하기** — 곱셈은 흰색으로 수렴하지 않는다. 주황 좀비가
   **밝은 주황**이 될 뿐이다. 흰 플래시는 가산이어야 한다.

그래서 이미션을 쓰는데, **`_EMISSION` 은 키워드라 MPB로는 못 켠다.** 미리 머티리얼에
켜 두고(`_UseEmission=1` + `EnableKeyword("_EMISSION")`) `_EmissionColor` 는 검정으로 둔다 —
평상시 외형은 전혀 안 바뀌고, MPB로 색만 흔들면 흰 플래시가 된다.

**적용된 머티리얼**: `Assets/monster/zombie1/tilemap_zombie1.mat`,
`Assets/monster/boss/boss_001/tilemap_zombie1 1.mat`.
**이 머티리얼을 다시 만들면 플래시가 조용히 죽는다** — 그때는 이미션을 다시 켤 것.

MPB를 쓰면 그 렌더러는 SRP 배처에서 빠진다. 플래시가 0.09초이고 발사 간격이 0.35초라
동시에 하얀 좀비는 몇 마리뿐이므로 프로토 단계에서는 문제되지 않는다.

### 넉백

`TakeDamage(amount, hitDir)` 로 **투사체 진행 방향**을 넘긴다 (`ProtoProjectile` 이 `_dir` 전달).
선형 감쇠라 이동 거리 = `speed × time / 2` → `speed = 2 × Dist / Time`.

- **추격 중이든 접촉 중이든 똑같이 적용한다.** 접촉 분기에서 빼면 플레이어에게 붙은 좀비는
  아무리 쏴도 꿈쩍하지 않는다.
- 넉백 변위도 `ProtoObstacles.Resolve` 를 통과하므로 벽을 뚫고 밀려나지 않는다.
- `ProtoGrid` 가 `LateUpdate` 에서 분리 + 아레나 클램프를 다시 적용하므로, 물량 속 좀비는
  넉백이 상쇄된다 — 의도한 동작이다.

### 풀 재사용 주의

`Spawn()` 에서 `ClearFlash()` 와 넉백 상태를 반드시 리셋한다. 안 하면 **하얀 채로 등장하는
좀비**가 나온다. 플래시 만료 처리는 `_dying` 분기보다 **먼저** 해야 한다 — 마지막 일격이
치명타면 하얀 채로 사망 애니메이션을 재생하게 된다.

`Awake` 는 에디터에서 호출되지 않으므로 캐시는 `EnsureCache()` 로 지연 생성한다
(스폰 디렉터가 `AddComponent<ProtoZombie>()` 로 붙이는 구조라 더 그렇다).

## 세트피스 충돌 (`ProtoBlocker`)

`_Props` 계층 밖에 있는 큰 세트피스(호수 디오라마 등)용. 컴포넌트를 붙여 막을 영역을 **직접**
지정한다 — 렌더러 바운즈 자동 생성은 이런 것에 통하지 않는다 (디오라마 전체 바운즈는
11.3×11.7 이라 절벽 뒤 빈 공간까지 막는 상자가 된다).

| 필드 | 의미 |
|---|---|
| `shape` | `Box` (직선 벽) / `Ellipse` (둥근 것) |
| `halfExtents` | 로컬 XZ 반경. `lossyScale` 이 곱해진다 |
| `center` | 로컬 XZ 오프셋 |

`ProtoObstacles.Rebuild()` 가 `FindObjectsOfType<ProtoBlocker>()` 로 모아 프롭 박스와 같은
배열에 넣는다. 프롭 루트(`_Props`)가 없어도 블로커는 수집한다.

**둥근 것은 `Ellipse` 를 쓸 것.** 둥근 사각형인 호수 림을 박스로 덮으면 네 모서리에 1m 넘는
보이지 않는 벽이 생긴다. 타원 밀어내기는 로컬 좌표를 단위원 공간으로 정규화한 뒤 반경 방향으로
경계까지 밀어낸다 — 최근접점은 아니지만 안정적이고 미끄러짐이 자연스럽다.

**볼륨끼리 겹치지 않게 할 것.** 겹치면 A 가 밀어낸 곳이 B 안이고 B 가 밀어낸 곳이 A 안이라
`iterations` 안에 수렴하지 못하고 지오메트리에 갇힌다. 호수 디오라마는 `WaterSetup` 이
절벽 박스의 z 범위를 림 바운즈에서 클립해 겹침을 없앤다.

## 검증 (플레이 모드 실측)

- 충돌 박스 76개 생성. 밴 중심 방향으로 200스텝 밀어붙여도 중심에서 4.47m 밖에 머물고 벽을 따라 미끄러짐
- 링: 96 tris, `Proto/OverlayUnlit`, 좀비 8마리를 겹쳐 세워도 링이 관통해 보임
- 링 큐 4000 / 캐릭터·무기 큐 4001 확인 — 링이 캐릭터를 덮지 않고, 캐릭터는 앞의 좀비에 정상 가려짐
- 호수 블로커: 8방향에서 400스텝 밀어붙여도 중심에서 6.18~6.48m 밖에 머물고, 호수 한가운데에
  스폰시켜도 밀려난 뒤 10스텝 이동량 0.0000m (진동 없음)

## 참고 — Unity `??` 함정

`GetComponent<T>() ?? AddComponent<T>()` 패턴은 **동작하지 않는다.** Unity 오브젝트는
컴포넌트가 없을 때 C# 기준 null 이 아닌 '가짜 null' 을 돌려주므로 `??` 가 오른쪽을 평가하지
않고, 그 뒤 접근에서 `MissingComponentException` 이 난다. Awake 에서 예외가 나면 Unity 가
그 컴포넌트를 조용히 비활성화하므로 원인을 찾기 어렵다.

반드시 이렇게 쓸 것:

```csharp
var mf = gameObject.GetComponent<MeshFilter>();
if (mf == null) mf = gameObject.AddComponent<MeshFilter>();
```

이 프로젝트에서 같은 패턴 5곳을 이 이유로 고쳤다.

## 좀비 상호 밀어내기 (`ProtoGrid`)

균일 공간 해시 그리드. 90마리 전수 비교는 4,005쌍이지만 각 좀비가 주변 3×3 셀만 보므로
실측 비교 수가 수십 쌍 수준으로 떨어진다.

- 셀 크기 `1.0m`(분리 거리 0.62m보다 크게 → 3×3 이웃으로 충분), 월드 반경 22m
- **배열 기반 카운팅 소트** — 매 프레임 할당이 없다. GDD §16 의 Job 구조로 옮길 때 그대로 재사용 가능
- `LateUpdate` 에서 실행한다. `Update` 중에 풀면 같은 프레임에 다시 겹친다
- 밀어낸 뒤 아레나 클램프 + 프롭 충돌을 다시 적용해 벽을 뚫고 밀려나지 않게 한다

강도 `0.55` 는 의도적으로 1보다 낮다. 1이면 즉시 완전 분리되지만 좀비가 떨린다.
그 결과 평형 간격이 목표(0.62m)보다 약간 짧게 유지된다 — **실측 0.591m.**

**검증:** 좀비 8마리를 0.05m 간격으로 겹쳐 놓고 한 프레임 뒤 측정 → 전체 최소 간격 0.591m,
300쌍 중 6쌍만 목표 미달.

`separateZombies` 를 끄면 이전처럼 한 점에 뭉친다.

## 시작 시 카메라가 튀던 문제 — 해결

증상: Play 직후 화면이 한 번 툭 밀렸다.

`ProtoStartupDiag` 로 첫 40프레임을 기록해 원인을 특정했다:

```
frame 0:  cam.z = -11.764
frame 1:  cam.z = -10.364   ← 정확히 +1.4m
```

1.4m 는 `ProtoCameraFollow.leadDistance` 다. 원인은 `ProtoPlayer._lastMoveDir` 를
`Vector3.forward` 로 초기화한 것 — **입력이 없어도 카메라가 리드 오프셋을 최대로 적용**했다.
플레이어·비주얼 위치는 (0,0,0) 에서 전혀 흔들리지 않았으므로 캐릭터가 아니라 카메라 문제였다.

수정:

| 프로퍼티 | 의미 | 쓰는 곳 |
|---|---|---|
| `MoveDir` | **이번 프레임의 실제 이동 방향** (정지 중 zero) | 카메라 리드 |
| `FacingDir` | 마지막으로 움직인 방향 (0 이 되지 않음) | 스폰 링 앞/뒤 배분 |

정지 중 리드가 0 이 되어 시작 위치와 목표 위치가 일치하므로 점프가 사라진다.
**검증:** 40프레임 전부 `-11.764` 유지.

## 프레임 시간 상한 (`ProtoConfig.Delta`)

씬 로드 직후 `deltaTime` 이 **60~70ms** 까지 튄다(실측). 그대로 이동에 곱하면 캐릭터가
한 프레임에 수십 cm 순간이동한다. `ProtoConfig.Delta` 가 50ms(20fps 상당)로 클램프한다.

**이동·보간에는 `Time.deltaTime` 을 직접 쓰지 말고 `ProtoConfig.Delta` 를 쓸 것.**
현재 적용: 플레이어 이동, 좀비 이동, 투사체, 젬 자석, 카메라 보간, 밀어내기.

## 주의 — 에디터 포커스와 플레이 모드

**Unity 에디터가 포커스를 잃으면 플레이 모드가 틱하지 않는다.** `PlayerSettings.runInBackground`
는 스탠드얼론 빌드용이라 에디터에는 효과가 없다(켜 두었지만 무효).

그래서 자동화로는 FPS 같은 시간 기반 측정이 불가능하다. 실제로 `Time.frameCount` 가 2에서
멈춘 채로 관측된 적이 있고, 그때 측정한 프레임 시간(2,952ms)은 전부 무의미한 값이었다.
**성능을 볼 때는 Unity 창을 포커스한 상태로 직접 Play 할 것.**

(2026-11-20: `ProtoStartupDiag` 는 원인을 찾은 뒤라 지웠다 — 다시 쓰려면 `_Backup/20261120_CodeCleanup` 에서 되살린다.) 시간 기반 진단이 필요하면 `ProtoStartupDiag` 를 `_ProtoSystems` 에 붙이면 첫 40프레임을

## 화염 — 스프라이트 판 (`ProtoFlameSprite`) · 비교용 두 번째 구현

같은 불을 **쿼드 한 장 + 15칸 플립북**으로 그린다. 파티클 판(`ProtoFlameCone`)은
**그대로 살아 있고**, 옵션 `ProtoSettings.FlameStyle` 로 둘을 바꿔 끼운다.

두 구현 모두 `IProtoFlameFx`(Configure/Pulse) 만 구현한다. **판정은 어느 쪽도 건드리지
않는다** — 데미지는 `ProtoShooter.FireCone` 이 콘 수치로 직접 계산한다. 그래야 비교에
의미가 있다.

```
옵션 FlameStyle  0 = 파티클(기본)   1 = 스프라이트
ProtoShooter.ApplyWeapon 이 옵션을 보고 하나만 붙인다.
Update 에서 옵션 변화를 감지해 무기가 그대로여도 다시 붙인다 (게임 중 전환).
```

### 불이 나가는 자리를 총구로 옮겼다 (2026-09-18)

전에는 `transform.localPosition = (0, 0.36, 0)` — 플레이어 발밑에서 36cm 위였고, 그래서
불이 바닥에서 나왔다.

**1차 시도(실패): 인스펙터의 `ProtoShooter.muzzle` 을 썼다.** 투사체가 쓰는 점이니 맞겠거니
했는데, 재 보니 `Player` 바로 아래 손으로 박아 둔 고정점이었고 **높이 y=1.050 이 Head 본
(y=1.040)과 같은 자리**였다. 손 본은 `(0.498, 0.956, -0.065)` 로 전혀 다른 곳이다.
그래서 불이 총이 아니라 **입에서 뿜는 것처럼** 보였다. 총알은 작고 빨라서 아무도 눈치
못 챘을 뿐, 같은 자리에서 나가고 있었다.

**2차(적용): 장착된 무기 모델에서 총열 끝을 직접 찾는다** (`ProtoShooter.TryFindBarrelTip`).

- 무기 렌더러들의 메시 바운드를 무기 로컬 공간에 모아 **가장 긴 축을 총열**로 본다.
- 어느 쪽 끝이 총구인가는 **손에서 먼 쪽**으로 고른다. 처음엔 "캐릭터 정면으로 더 나간 쪽"
  으로 골랐는데 **바인드 포즈에서는 팔이 옆으로 뻗어 총열이 월드 X 를 향하므로** 뒤집혔다.
  손은 손잡이를 쥐고 있으니 총구는 언제나 손에서 먼 쪽이고, 이 기준은 자세와 무관하다.
- 찾은 자리에 `MuzzleAuto` 빈 오브젝트를 만들어 **무기의 자식으로 붙인다.** 그러면 애니메이션
  추적을 트랜스폼 계층이 공짜로 해 준다 — `Update` 에서 월드 좌표를 계산하면 애니메이터가
  그 뒤에 본을 움직여서 총구가 한 프레임 늦는다.
- 붙이기가 거부되면(에디터에서는 무기가 프리팹 인스턴스 안이라 막힌다) `_muzzleParented`
  가 false 로 남고 매 프레임 `TransformPoint` 로 따라간다. **거부를 확인 안 하고
  `localPosition` 을 넣으면 총구가 엉뚱한 월드 좌표로 날아간다.**

실측(화염방사기): 총열 끝이 손잡이에서 **0.415m** (무기 전체 길이 0.458m). 소총도 0.299m 로
제자리를 찾는다.

대비 순서는 `무기 총열 끝` → `인스펙터 muzzle` → `발밑 1m` 다. 무기는 `WeaponSocket` 이
**런타임에** 붙이므로 처음 몇 프레임이 대비책으로 도는 것은 정상이다.

### 총알도 총구에서 나가게 했다 · 부채꼴 꼭짓점은 플레이어로 남겼다

**`Origin()` 이 `AutoMuzzle` 을 쓴다.** 총알·발사음·화염이 모두 같은 점에서 나간다.
예전에는 셋 다 머리 높이에서 나가고 있었다.

**부채꼴 꼭짓점을 총열 끝으로 옮기는 것은 시도했다가 되돌렸다.** 총은 몸 중심에서 0.46m
옆으로 치우쳐 쥐고 있어서, 거기를 꼭짓점으로 삼으면 **코앞의 좀비가 판정에서 빠진다.**
실측으로 확인했다 — 정면 0.4m / 0.6m / 0.8m 가 전부 판정 밖이 됐다(1m 앞의 0.46m 치우침은
각도로 25°인데 부채꼴 반각은 15°다). 좀비 최소 접근 거리가 0.60m(몸 0.28 + 플레이어 0.32)라
실제로 닿는 구멍이다.

**대신 불줄기 길이를 줄여서 맞췄다** (`ProtoFlameCone.Reach`). 판정은 플레이어에서
`st.range` 까지인데 그림은 총구에서 시작하므로, 총구가 앞선 만큼 빼면 **불끝과 판정 끝이
같은 자리**에 온다. 스프라이트 판도 같은 계산을 쓴다.

```
불이 뻗는 길이 = st.range − clamp(화염원점.localPosition.z, 0, st.range/2)
```

옆으로 치우친 것은 보정하지 않는다 — 그것까지 맞추려면 콘을 기울여야 하는데 그러면
플레이어 중심 부채꼴인 판정과 더 어긋난다. 자세에 따라 총구가 뒤로 갈 수도 있어 0 으로 자른다
(그때는 예전처럼 `st.range` 그대로 뻗는다).

### 콘 폭을 50° → 30° 로 좁혔다 (2026-09-18) · 입자 크기를 부채꼴 폭에 묶었다

불이 너무 넓게 퍼진다는 판단으로 `WS_Flamethrower.coneDegrees` 를 **50 → 30** 으로 내렸다.
`ProtoShooter.FireCone` 이 같은 값으로 판정하므로 **데미지 범위도 같이 40% 줄었다** — 밸런스
변경이다. 그림만 좁히는 선택지도 있었지만, 보이지 않는 곳에서 맞는 무기가 되므로 안 했다.

같이 고친 것: 입자 크기가 **사거리에만** 걸려 있어서(`range * 0.32`) 콘을 좁히면 입자가
부채꼴보다 커져 불이 판정 밖으로 삐져나왔다(콘 30°일 때 부채꼴 2.41m 대 입자 1.44m).
이제 **부채꼴 폭에서 뽑는다** — `sz = fanW * 0.343`. 계수는 콘 50° 기준 환산값이라
예전 각도에서는 그림이 한 픽셀도 안 바뀐다.

| | 부채꼴 폭 | 입자 크기 | 칠한 화소 | 화면 대비 | 델타 |
|---|---|---|---|---|---|
| 이전 콘 50° | 4.20m | 1.44m | 1,429,565 | 68.9% | +0.169 ms |
| **적용 콘 30°** | **2.41m** | **0.83m** | **481,458** | **23.2%** | +0.167 ms |

**채우기 66% 감소.** 1080p 데스크톱 시간으로는 이게 잘 안 보인다 — 반복 측정에서
콘50° 대비 100%(차이 없음)부터 73%까지 나왔다. 잡음 구간이다.

**해상도를 올려 채우기를 지배적으로 만들면 인과가 드러난다** (각 16라운드 교차, 최소값):

| 해상도 | 불 없음 | 콘 50° | 콘 30° | 콘30°/콘50° |
|---|---|---|---|---|
| 1280×720 | 1.822 | +0.225 | +0.166 | 74% |
| 1920×1080 | 2.432 | +0.209 | +0.152 | 73% |
| 3840×2160 | 6.022 | +0.443 | +0.281 | 63% |
| 5760×3240 | 11.431 | +0.691 | +0.351 | **51%** |

채우기가 지배할수록 칠한 화소 비율(34%)에 수렴한다. **입자 수는 그대로(146→148)라
입자당 제출 비용은 하나도 안 줄었고**, 그게 저해상도에서 74% 에 머무는 이유다.

> **측정 방법으로 기억할 것**: 채우기를 줄이는 최적화는 데스크톱 1080p ms 로는 안 보인다.
> 칠한 화소를 따로 세거나 해상도를 올려서 봐야 한다.

> 참고: **콘 각도만 좁히면 비용이 안 준다.** 칠한 화소는 입자 넓이의 합이라 퍼짐과 무관하다.
> 실측으로 콘만 50°→30° 로 줄였을 때 69.9% → 66.2% 로 거의 그대로였다.
> 줄인 것은 같이 내려간 **입자 크기**다(채우기는 크기의 제곱).

### 고침: 파티클 판이 실제 게임에서 **25% 듀티로 깜빡이고 있었다** (2026-09-18 수정)

`ProtoShooter` 는 발사 간격(0.2초)마다 `Pulse()` 를 부르는데 `ProtoFlameCone` 의 판정은
`Time.time - _lastPulse < 0.05f` 다. 즉 **0.05초 켜고 0.15초 끈다.**

| | 입자 수 |
|---|---|
| 연속 방출(정상 상태) | 149알 |
| 실제 게임의 25% 듀티 | **23알 (15%)** |

전에 "여러 개 불이 좁게 나가는 것 같다"고 했던 것의 원인이 이쪽이다 — 입자 밀도가
1/6 이라 불이 이어지지 않고 덩어리 몇 개로 끊긴다. `ProtoFlameCone` 안에 `FadeInTime`
/`FadeOutTime`(0.08/0.28)과 `_fade` 가 있는데 **계산만 하고 아무 데도 쓰지 않는다** —
원래는 이걸로 메우려던 것으로 보인다.

**고쳤다.** `ProtoFlameCone.HoldTime = 0.30f` (발사 간격 0.20초보다 길다). 죽어 있던
`_fade`/`FadeInTime`/`FadeOutTime` 은 같이 걷어냈다 — 방출만 멈추면 남은 입자가 제 수명
(0.60~0.74초)만큼 타다 꺼지므로 따로 페이드를 만들 필요가 없다.

| | 입자 | 칠한 화소 | 화면 대비 | 델타 |
|---|---|---|---|---|
| 고치기 전 | 23알 | 269,657 | 13.0% | +0.072 ms |
| **고친 뒤** | **146알** | **1,566,175** | **75.5%** | **+0.170 ms** |

불이 한 덩어리로 이어지는 대신 **칠하는 화소가 5.8배**가 됐다. 데스크톱에서는 여전히 작지만
모바일에서 화염이 프레임을 갉아먹으면 여기가 원인이다. 줄이는 손잡이는 입자 **크기**다
(`ConfigureJet` 의 `sz = st.range * 0.32f`) — 채우기는 크기의 제곱으로 줄어서 개수를 줄이는
것보다 훨씬 잘 듣는다. 그다음 후보가 스프라이트 판(`ProtoFlameSprite`, 화면의 5.7%)이다.

깜빡임을 고치기 **전에는** 둘 다 잡음 안이라 우열이 없었다(파티클 23알 = 화면의 13%).
고친 뒤로는 칠하는 화소가 13배 차이 난다. 그래도 **파티클을 쓰기로 했다 — 그림이 낫다.**
파티클은 겹쳐 그리는 양이 곧 비용이고, 플립북은 겹침이 항상 1배다.

> `ProtoRainFx` 주석에 적어 뒀던 "화염은 채우기 지배라 쿼드로 바꿔도 안 싸진다"는
> **틀린 예측이었다.** 채우기 지배라는 관찰 자체는 맞았지만, 그 채우기의 정체가
> *입자끼리의 겹침*이라는 것을 건너뛰고 읽었다. 플립북은 바로 그 겹침을 없앤다.

### 조준축 빌보드의 약점을 카메라가 막아 준다

쿼드는 조준 방향을 축으로 삼아 그 축 둘레로만 돌아 카메라를 본다. 축이 시선과 겹치면
쿼드가 옆으로 서서 사라지는 게 이 방식의 고질병인데, 이 게임은 카메라가 37~58° 내려보고
제트는 수평이라 **겹칠 수가 없다**. 네 방향 실측에서 최악이 0.56 이었다.

- `groundLie` 1 로 두면 쿼드가 판정 부채꼴과 똑같이 바닥에 눕는다. 판정과 정확히 겹치지만
  카메라 각도에 따라 그림이 짜부라진다(조준 방향에 따라 화면상 비율 1.26 ~ 0.91).
- `upAxis.y < 0` 일 때 뒤집는 보정이 있다. 카메라 정면으로 쏘는 한 순간에만 부호가
  바뀌는데, 그때 쿼드는 이미 거의 바닥에 누워 있어서 눈에 안 띈다.
